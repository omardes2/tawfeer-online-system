# رحلات المستخدمين (User Journeys) — Tawfeer Online

> **وثيقة توثيقية فقط (Documentation Only).** لا تحوي كودًا ولا هجرات. تلتزم بالكامل بـ [`ARCHITECTURE.md`](../ARCHITECTURE.md) (المبادئ الـ14) و [`docs/DECISIONS.md`](DECISIONS.md) (المصدر الوحيد للحقيقة — ADRs والمفردات القانونية) و [`REQUIREMENTS.md`](../REQUIREMENTS.md) و [`docs/FOUNDATION_REPORT.md`](FOUNDATION_REPORT.md).
>
> أي مفتاح حالة (status key) أو صلاحية (permission key) مذكور هنا مأخوذ حرفيًا من المصادر أعلاه. المفاتيح التي تُسبق بعلامة (⏳ مقترح) هي امتدادات مصمّمة في ADRs ولم تُزرع بعد في `RolePermissionSeeder`، وتُضاف عند وصول مرحلتها.

## مرجع سريع — المفردات القانونية المستخدمة

**حالات الطلب (ADR-010):** `draft → new → awaiting_contact → awaiting_confirmation → confirmed → stock_reserved → preparing → ready_to_ship → shipped → out_for_delivery → delivered` + `delayed` · `customer_unavailable` · `cancelled` · `delivery_failed` · `returned` · `partially_returned` · `exchanged`.
> ملاحظة: بذور Phase 1 المزروعة (`pending, confirmed, processing, shipped, delivered, cancelled, returned`) مجموعة مبسّطة تُوسَّع لتطابق ADR-010 في Phase 3 (المبدأ 10 — الحالات بيانات لا Enum).

**حالات الدفع (Phase 1 seed):** `unpaid → partially_paid → paid` + `refunded`.
**حالات الشحن (Phase 1 seed):** `not_shipped → preparing → in_transit → delivered` + `failed`.
**حالات أمر الشراء (DECISIONS.md):** `draft → pending_approval → approved → partially_received → received → closed` + `cancelled`.
**حالات فاتورة المورد (Phase 4):** `draft → pending_approval → approved → partially_paid → paid` + `cancelled`.
**أنواع حركة المخزون (Movement Types):** `purchase_in · sale_out · transfer_out · transfer_in · adjustment_in · adjustment_out · reserve · release · return_in · damage_out`.
**حالات العمولة (ADR-012a):** `expected → pending → earned → approved → payable → paid` + `cancelled` · `reversed`.
**تدفّق الإرجاع (ADR-011):** `return_request → approved → received → inspected → (restock | to_damaged) → (refund | exchange | credit_note)`.
**دلاء المخزون (ADR-007):** `on_hand · reserved · available(=on_hand−reserved) · damaged · returned_pending · in_transit`.

**قنوات الإشعارات (المبدأ 11/13، ADR-018/019):** جميع الإشعارات تُطلق عبر أحداث دومين وتُعالَج في **طوابير (Queues)**، وتُرسل عبر عقود التكامل:
- **In-App / Database** (لوحة التحكم — كل الأدوار الداخلية).
- **البريد الإلكتروني (Email)**.
- **WhatsApp / SMS** عبر `MessagingContract` + Driver (المبدأ 13) — لا ربط مباشر.
- **الصندوق الموحّد (Unified Inbox / Omnichannel)** — WhatsApp / Messenger / Instagram (المتطلب 2.9).

**خريطة الأدوار (RolePermissionSeeder):** `admin` · `manager` · `sales` · `accountant` · `warehouse` · `affiliate` · `customer`. الأدوار غير المزروعة بعد (مشتريات، توصيل) تُشتق من صلاحياتها وتُوفَّر عند مرحلتها.

# 1. رحلة الزائر (Guest Customer — زائر)

**المرحلة:** Phase 3 (المتجر الإلكتروني والطلبات). الكتالوج المعروض من Phase 2.

### نقطة البداية
دخول غير مُصادَق (unauthenticated) إلى واجهة المتجر عبر رابط مباشر، بحث، أو رابط إحالة مسوّق (`?ref={code}`).

### الخطوات
1. تصفّح الصفحة الرئيسية والفئات (Categories) والمنتجات المتاحة.
2. البحث والفلترة والترتيب حسب السعر/الفئة/التوفّر.
3. فتح صفحة منتج: الصور، الوصف، المتغيّرات (Variants)، `retail_price`، والتوفّر المحسوب من `available`.
4. إضافة منتجات إلى السلة (Cart) — تُحفظ في الجلسة/الكوكيز (بلا حساب).
5. عند الرغبة بإتمام الشراء (Checkout): يُطلب تسجيل الدخول أو الشراء كضيف (Guest Checkout) أو إنشاء حساب.
6. إدخال بيانات الشحن (governorate → city → area — ADR-014) وحساب تكلفة الشحن من `shipping_zone`.
7. اختيار بوابة دفع (عبر `PaymentGatewayContract` — المبدأ 13) وتأكيد الطلب.
8. يُنشأ الطلب بحالة `new` (مصدر `channel = web`) ورقم مقروء `ORD-{YYYY}-{seq}` (ADR-002).

### الصلاحيات
- لا صلاحيات RBAC (زائر بلا دور). الوصول محصور بالموارد العامة المكشوفة عبر `uuid` لا `id` (المبدأ 4، ADR-002).
- التكلفة و`average_cost` و`min_price` غير مكشوفة إطلاقًا (ADR-013).

### تحقّقات النظام
- توفّر المتغيّر: `available = on_hand − reserved > 0` (ADR-007) قبل السماح بالإضافة/الطلب.
- السعر المعروض = `retail_price` (أو `promo_price` ضمن فترته) — لا بيع تحت `min_price` (ADR-006a).
- التحقق من نطاق الشحن (تغطية `shipping_zone` للمدينة/المنطقة).
- كشف تكرار الطلب (Idempotency) عند الضغط المزدوج على «تأكيد».
- إنشاء الطلب داخل `DB::transaction()` مع قفل صف المخزون عند الحجز (المبدأ 7).

### الإشعارات
- تأكيد الطلب للزائر عبر Email/WhatsApp (`MessagingContract`).
- إشعار In-App لموظف المبيعات بورود طلب جديد (`new`).
- في حال رابط إحالة: تُسجَّل نقرة/تحويل للمسوّق (عمولة `expected` — ADR-012a).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| نفاد المخزون أثناء الدفع | رفض التأكيد + رسالة «الكمية غير متاحة» + عدم إنشاء حجز. |
| فشل بوابة الدفع | يبقى الطلب `new`/`draft` بحالة دفع `unpaid` مع إمكانية إعادة المحاولة. |
| مدينة خارج نطاق التغطية | منع إتمام الشراء + اقتراح تواصل يدوي. |
| ضغط مزدوج | كشف التكرار ومنع طلب ثانٍ. |

### النتيجة النهائية
طلب بحالة `new` مربوط بعنوان شحن وبيانات تواصل، جاهز لمسار التأكيد (Phase 3)، مع إشعار للعميل والمبيعات. الزائر قد يُحوَّل إلى «عميل مسجّل» إن أنشأ حسابًا.

# 2. رحلة العميل المسجّل (Registered Customer — عميل مسجّل)

**الدور:** `customer` (بلا صلاحيات لوحة داخلية — المبدأ 12). **المرحلة:** Phase 3.

### نقطة البداية
تسجيل الدخول (Sanctum/Breeze) إلى حساب العميل عبر الويب أو تطبيق موبايل مستقبلي (نفس `/api/v1` — المبدأ 11).

### الخطوات
1. تسجيل الدخول / استعادة كلمة المرور.
2. إدارة الملف الشخصي والعناوين المتعددة (area/city/governorate — ADR-014).
3. التصفّح والإضافة للسلة والمفضّلة (Wishlist).
4. إتمام الشراء من عنوان محفوظ ودفع عبر البوابة.
5. متابعة حالة الطلب عبر رقمه المقروء و`uuid` (تتبّع مباشر).
6. عرض سجل الطلبات والفواتير ونقاط الولاء (Promotions & Loyalty — المتطلب 2.10).
7. عند الاستلام: قد يفتح طلب إرجاع (`return_request` — ADR-011) ضمن نافذة الإرجاع.

### الصلاحيات
- يرى **طلباته فقط** (Policy على `Order` تربط `customer_id`) — لا وصول لطلبات الآخرين ولا للوحة الإدارة.
- لا رؤية تكلفة/هامش إطلاقًا (ADR-013).

### تحقّقات النظام
- ملكية المورد: كل استعلام مقيَّد بالعميل صاحب الحساب (Policy).
- توفّر المخزون وحد `min_price` كما في رحلة الزائر.
- نافذة الإرجاع مفتوحة (الطلب `delivered` وضمن المهلة) قبل قبول `return_request`.
- احتساب نقاط الولاء/الكوبونات ضمن الشروط والصلاحية.

### الإشعارات
- تأكيد الطلب، وتحديثات الحالة عند كل انتقال (`confirmed`, `shipped`, `out_for_delivery`, `delivered`) عبر Email/WhatsApp.
- إشعار قبول/رفض طلب الإرجاع والاسترداد.
- إشعارات ترويجية/ولاء (اختيارية حسب التفضيلات).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| محاولة الوصول لطلب ليس له | رفض 403 (Policy) + تدقيق (المبدأ 8). |
| إرجاع خارج النافذة | رفض `return_request` مع سبب. |
| دفع فاشل | حالة دفع `unpaid` + إعادة محاولة. |
| كوبون منتهٍ/غير مؤهّل | رفض التطبيق مع رسالة. |

### النتيجة النهائية
عميل يدير دورته الشرائية كاملة ذاتيًا (طلب → تتبّع → استلام → إرجاع اختياري) مع سجل موثّق وإشعارات متعددة القنوات.

# 3. رحلة موظف المبيعات (Sales Employee — موظف مبيعات)

**الدور:** `sales`. **الصلاحيات المزروعة:** `dashboard.view, orders.view, orders.manage, catalog.view, crm.view, crm.manage, messaging.view, messaging.manage`. **المرحلة:** Phase 3 (الطلبات/CRM/Omnichannel).

### نقطة البداية
تسجيل الدخول إلى لوحة التحكم؛ استقبال Lead جديد أو طلب `new` من المتجر أو رسالة من الصندوق الموحّد.

### الخطوات
1. مراجعة قائمة الطلبات الجديدة (`new`) وقائمة الـ Leads (CRM — المتطلب 2.7).
2. التواصل مع العميل (اتصال/واتساب من **الصندوق الموحّد** — Omnichannel، المتطلب 2.9): نقل الطلب إلى `awaiting_contact` ثم `awaiting_confirmation`.
3. إنشاء طلب يدوي (`channel = manual`) لعميل عبر الهاتف: يبدأ من `draft`/`new` وقد يتجاوز `awaiting_contact` (ADR-010).
4. اختيار المنتجات والمتغيّرات والكميات؛ يظهر `retail_price`/`wholesale_price` فقط (لا تكلفة — ADR-013).
5. تطبيق خصم/كوبون ضمن الحدود المسموحة.
6. تأكيد الطلب → `confirmed` ثم `stock_reserved` (حجز المخزون تلقائيًا — ADR-009).
7. ربط المحادثة بالعميل والطلب في CRM؛ تحديث مرحلة الفرصة (Opportunity/Pipeline).

### الصلاحيات
- `orders.manage` لإنشاء/تعديل الطلبات و`crm.manage` لإدارة العملاء والفرص و`messaging.manage` للصندوق الموحّد.
- **لا يملك `pricing.view_cost`** (⏳ مقترح) ⇒ التكلفة و`average_cost` و`min_price` محجوبة والتقارير الربحية محجوبة (ADR-013).
- البيع تحت `min_price` يتطلب `pricing.override_min_price` (⏳ مقترح) **وموافقة** (ADR-006a) — ليست ضمن دور المبيعات افتراضيًا.

### تحقّقات النظام
- **فرض الحد الأدنى (min-price):** يُمنع سعر بند < `min_price` إلا بصلاحية التجاوز + موافقة؛ كل محاولة تُسجَّل في التدقيق (ADR-006a, المبدأ 8).
- **منع السالب:** الحجز يُمنع إن جعل `available` سالبًا (ADR-007a) — إلا إذا فُعِّل `inventory.allow_negative` للمستودع.
- كشف تكرار العميل/الطلب (Duplicate detection) في CRM قبل إنشاء Lead/طلب.
- كل تأكيد + حجز داخل `DB::transaction()` مع قفل صف المخزون (المبدأ 7).

### الإشعارات
- إشعار العميل بتأكيد الطلب (Email/WhatsApp).
- إشعار In-App لأمين المستودع بطلب محجوز جاهز للتجهيز.
- تنبيه لمدير المبيعات عند طلب تجاوز `min_price` (طلب موافقة).
- رسائل الصندوق الموحّد الواردة تظهر فورًا وتُعيَّن للموظف.

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| محاولة بيع تحت `min_price` بلا صلاحية | رفض + تسجيل تدقيق + طلب موافقة المدير. |
| نقص مخزون عند الحجز | رفض `stock_reserved` + عرض المتاح الفعلي. |
| محاولة رؤية التكلفة/الربح | حجب الحقول والتقارير (ADR-013). |
| عميل مكرّر | دمج/تنبيه بدل إنشاء مكرّر. |

### النتيجة النهائية
طلب `confirmed → stock_reserved` مربوط بعميل ومحادثة CRM، جاهز للتجهيز في المستودع، مع مسار عمولة `expected` إن كان عبر مسوّق.

# 4. رحلة مدير المبيعات (Sales Manager — مدير مبيعات)

**الدور:** `manager`. **الصلاحيات المزروعة:** `dashboard.view, users.view, catalog.view, catalog.manage, inventory.view, inventory.manage, orders.view, orders.manage, purchasing.view, crm.view, reports.view, audit.view`. **المرحلة:** Phase 3.

### نقطة البداية
لوحة تحكم إشرافية: طلبات موافقة معلّقة، مؤشرات أداء الفريق (KPIs)، وطلبات تجاوز الأسعار.

### الخطوات
1. مراجعة لوحة KPI للمبيعات (تحويل، متوسط قيمة الطلب، أداء الموظفين) — المتطلب 2.11.
2. اعتماد/رفض طلبات تجاوز `min_price` أو الخصومات الاستثنائية (سير موافقة — APPROVAL_WORKFLOWS).
3. مراقبة انتقالات الطلبات ومعالجة العالقة (`delayed`, `awaiting_contact` المتأخرة).
4. إعادة تعيين الطلبات/المحادثات بين موظفي المبيعات.
5. الاطلاع على سجل التدقيق (`audit.view`) لعمليات الأسعار والطلبات الحسّاسة.
6. مراجعة تقارير المبيعات وتصديرها (PDF/Excel).

### الصلاحيات
- `orders.manage` + `reports.view` + `audit.view` + `catalog.manage`/`inventory.manage` (إشراف واسع).
- **لا يملك `pricing.view_cost`** افتراضيًا (⏳ مقترح): إن لم تُمنح، تبقى الربحية محجوبة حتى للمدير (ADR-013) — تُمنح صراحةً عند الحاجة.
- منح الموافقة على تجاوز `min_price` يتطلب أن يملك (أو يُفوَّض) `pricing.override_min_price` (⏳ مقترح).

### تحقّقات النظام
- صحة انتقالات الحالة عبر State Machine المقروءة من قاعدة البيانات (ADR-017).
- كل موافقة تُسجَّل في التدقيق مع القيمة قبل/بعد (المبدأ 8).
- التحقق من أن التجاوز ضمن سياسة السعر (لا يقل عن حد صلب مطلق إن وُجد).

### الإشعارات
- إشعار الموظف بنتيجة طلب الموافقة (اعتماد/رفض).
- تنبيهات In-App بالطلبات المتأخرة أو المتوقفة.
- ملخّصات دورية للأداء (Email).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| موافقة على سعر تحت الحد الصلب المطلق | رفض النظام حتى مع الموافقة (حد صارم). |
| تفويض صلاحية غير مملوكة | منع (المبدأ 12 — RBAC لا أسماء). |
| تعديل طلب بعد `shipped` | رفض تعديل البنود (يُعالَج كإرجاع/استبدال — ADR-010). |

### النتيجة النهائية
إشراف مُحكم على دورة المبيعات: موافقات موثّقة، فريق مُدار، ومؤشرات أداء واضحة مع أثر تدقيق كامل.

# 5. رحلة أمين المستودع (Warehouse Employee — أمين مستودع)

**الدور:** `warehouse`. **الصلاحيات المزروعة:** `dashboard.view, inventory.view, inventory.manage, purchasing.view, orders.view`. **المرحلة:** Phase 2 (المخزون) + Phase 3 (تجهيز الطلبات).

### نقطة البداية
لوحة المستودع: أوامر شراء معتمدة بانتظار الاستلام، طلبات محجوزة بانتظار التجهيز، وتنبيهات حد إعادة الطلب.

### الخطوات
1. **استلام بضاعة (GRN):** استلام أصناف مقابل أمر شراء `approved` → حركة `purchase_in`، تحديث `on_hand`، وإعادة حساب `average_cost` (WAC — ADR-005) مع التكلفة المُحمّلة (Landed Cost).
2. تحديث حالة أمر الشراء إلى `partially_received` أو `received` (DECISIONS.md).
3. **تجهيز الطلبات (Phase 3):** لطلب `stock_reserved` → `preparing` → `ready_to_ship`؛ عند الشحن الفعلي `shipped`: خصم نهائي `on_hand -= qty`, `reserved -= qty`، واحتساب COGS بـ WAC (ADR-009).
4. **التحويل بين المستودعات:** حركة `transfer_out` من المصدر (يزيد `in_transit`) ثم `transfer_in` في الوجهة، برقم `TRF-{YYYY}-{seq}` (ADR-002).
5. **الجرد والتسوية:** فروق الجرد عبر `adjustment_in`/`adjustment_out` برقم `ADJ-{YYYY}-{seq}`.
6. **التالف والمرتجع:** نقل إلى `damaged` (`damage_out`) أو استقبال مرتجع (`return_in` → `returned_pending` ثم فحص → `restock`/`to_damaged` — ADR-011).

### الصلاحيات
- `inventory.manage` لكل حركات المخزون؛ `orders.view` لرؤية الطلبات المطلوب تجهيزها؛ `purchasing.view` لمطابقة أمر الشراء عند الاستلام.
- لا يعتمد أوامر الشراء (لا `purchasing.manage`) ولا يرى التقارير المالية.
- رؤية التكلفة عند الاستلام محكومة بـ `pricing.view_cost` (⏳ مقترح، ADR-013) — قد يرى تكلفة الاستلام دون هوامش البيع.

### تحقّقات النظام
- **منع السالب (ADR-007a):** يُمنع أي صرف/تحويل يجعل `available` سالبًا إلا بتفعيل `inventory.allow_negative` للمستودع؛ كل حركة داخل معاملة مع `lockForUpdate` (المبدأ 7).
- كل حركة تُنتج قيدًا في `inventory_ledger` (append-only، ADR-008) مع الرصيد الجاري و WAC بعد الحركة.
- مطابقة الكمية المستلمة ≤ المطلوبة في أمر الشراء (كشف زيادة/تكرار استلام).
- الدلاء `damaged`/`returned_pending`/`in_transit` لا تُحتسب ضمن المتاح للبيع (ADR-007).

### الإشعارات
- تنبيه In-App عند بلوغ حد إعادة الطلب (Reorder Point) → لموظف المشتريات.
- إشعار المبيعات/العميل عند شحن الطلب (`shipped`).
- إشعار الوجهة عند وصول تحويل (`transfer_in` مطلوب).
- تنبيه المدير عند تسوية جرد كبيرة (تدقيق — المبدأ 8).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| صرف يتجاوز المتاح | رفض الحركة (ADR-007a) + رسالة بالمتاح. |
| استلام أكثر من المطلوب | رفض/تنبيه ومطابقة مع أمر الشراء. |
| كسر المعاملة (خطأ أثناء الحركة) | Rollback كامل — لا رصيد نصفي (المبدأ 7). |
| تحويل بلا مستودع وجهة صالح | رفض. |

### النتيجة النهائية
أرصدة مخزون دقيقة لكل (متغيّر × مستودع) مع WAC محدّث ودفتر مخزون متكامل؛ طلبات مُجهّزة ومشحونة، وتحويلات وتسويات موثّقة.

# 6. رحلة موظف المشتريات (Purchasing Employee — موظف مشتريات)

**الدور:** يُشتق من صلاحيات `purchasing.view, purchasing.manage` (⏳ دور «purchasing» غير مزروع بعد في `RolePermissionSeeder`؛ `purchasing.manage` متاح للـ`admin` حاليًا — يُوفَّر دور مخصّص في Phase 2/4). **المرحلة:** Phase 2 (أوامر الشراء) + Phase 4 (فواتير الموردين).

### نقطة البداية
لوحة المشتريات: تنبيهات نقص المخزون (Reorder)، الموردون، وأوامر الشراء المسودّة.

### الخطوات
1. إدارة سجل الموردين (Suppliers) وجهات الاتصال وشروط التعامل.
2. إنشاء أمر شراء (PO) بحالة `draft`، رقم `PO-{YYYY}-{seq}` (ADR-002)، وإضافة الأصناف والكميات وأسعار الشراء.
3. رفع الأمر للاعتماد → `pending_approval`.
4. بعد اعتماد المدير → `approved`، وإرسال الأمر للمورد.
5. متابعة الاستلام (من أمين المستودع): تتحول الحالة تلقائيًا إلى `partially_received` ثم `received`.
6. توزيع **التكلفة المُحمّلة (Landed Cost)** — شحن/جمارك/استيراد — على الأصناف حسب `purchasing.landed_allocation` (قيمة/وزن/كمية — ADR-005).
7. **(Phase 4)** تسجيل فاتورة المورد ومطابقتها بأمر الشراء والاستلام (3-way match) → `draft → pending_approval → approved`.
8. إغلاق الأمر → `closed` بعد اكتمال الاستلام والفوترة.

### الصلاحيات
- `purchasing.manage` لإنشاء/تعديل أوامر الشراء والموردين؛ `inventory.view` لمتابعة الأرصدة.
- **لا يعتمد أمره بنفسه** — الاعتماد بيد المدير/المدير العام (فصل الواجبات — Segregation of Duties).
- يرى تكلفة الشراء (بحكم دوره) لكن ليس بالضرورة هوامش البيع (ADR-013 — `pricing.view_cost` منفصل).

### تحقّقات النظام
- منع اعتماد الأمر من مُنشئه نفسه (فصل الواجبات).
- التسلسل الرقمي (`PO-{YYYY}-{seq}`) يُولّد داخل معاملة مع قفل لمنع التكرار (ADR-002، المبدأ 7).
- الكمية المستلمة الكلية ≤ كمية الأمر (وإلا `partially_received`/رفض الزيادة).
- كشف تكرار الفاتورة (رقم فاتورة المورد فريد لكل مورد — Phase 4).
- كل تغيّر على المورد/السعر/الأمر يُدقَّق (Auditable — ADR-020).

### الإشعارات
- إشعار المدير بطلب اعتماد أمر شراء (`pending_approval`).
- إشعار موظف المشتريات بنتيجة الاعتماد (`approved`/`cancelled`).
- إشعار أمين المستودع بأمر معتمد بانتظار الاستلام.
- تنبيه المحاسب عند وصول فاتورة مورد للاعتماد/الدفع (Phase 4).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| اعتماد ذاتي | رفض (فصل الواجبات). |
| فاتورة مكرّرة | كشف ومنع (رقم فريد لكل مورد). |
| استلام يتجاوز الأمر | رفض/إبقاء `partially_received`. |
| إلغاء أمر مستلَم جزئيًا | لا حذف — `cancelled` مع الحفاظ على حركات الاستلام المنفّذة (ADR-016). |

### النتيجة النهائية
دورة شراء موثّقة: `draft → pending_approval → approved → (partially_)received → closed`، مع مخزون مُستلَم بتكلفة محمّلة صحيحة تغذّي WAC، وأثر محاسبي مصمّم للقيد لاحقًا (ADR-016).

# 7. رحلة المحاسب (Accountant — محاسب)

**الدور:** `accountant`. **الصلاحيات المزروعة:** `dashboard.view, accounting.view, accounting.manage, orders.view, purchasing.view, reports.view`. **المرحلة:** Phase 4 (فواتير/مدفوعات) + Phase 5 (القيد المزدوج). البنية مصمّمة الآن (ADR-016).

### نقطة البداية
لوحة المحاسبة: فواتير موردين معتمدة بانتظار الدفع، مقبوضات معلّقة، وتقارير مالية.

### الخطوات
1. إدارة دليل الحسابات (Chart of Accounts) والخزائن والبنوك (Phase 5).
2. مراجعة فواتير المبيعات الناتجة عن الطلبات (الاعتراف بالإيراد عند `delivered` — ADR-010a).
3. **(Phase 4)** تسجيل مدفوعات الموردين مقابل فواتير `approved`: `partially_paid → paid`.
4. تسجيل المقبوضات من العملاء وتحديث حالة الدفع (`unpaid → partially_paid → paid`).
5. معالجة الاستردادات (`refunded`) الناتجة عن مرتجع مقبول (عكس الإيراد وCOGS نسبيًا — ADR-011).
6. **(Phase 5)** مراجعة/ترحيل القيود المزدوجة (Double-Entry) الناتجة آليًا عن أحداث الدومين (استلام بضاعة، بيع، تحصيل، دفع، عمولة، إرجاع — ADR-016).
7. إخراج التقارير: ميزان المراجعة، قائمة الدخل، الميزانية العمومية (المتطلب 2.6).

### الصلاحيات
- `accounting.manage` للقيود والمدفوعات؛ `orders.view`/`purchasing.view` للمطابقة؛ `reports.view` للتقارير المالية.
- يرى التكلفة والربحية بحكم الدور المحاسبي (على عكس المبيعات — ADR-013).
- لا يعدّل حركات المخزون (لا `inventory.manage`).

### تحقّقات النظام
- **العكس لا الحذف (ADR-011/016):** لا تُحذف معاملة مالية معتمدة؛ تُنشأ قيود عكسية. الدفاتر append-only بلا Soft Delete (ADR-020).
- توازن القيد المزدوج (مجموع المدين = مجموع الدائن) قبل الترحيل (Phase 5).
- منع دفع يتجاوز رصيد الفاتورة (`paid` ≤ إجمالي الفاتورة).
- الاعتراف بالإيراد حصريًا عند `delivered` لا عند الإنشاء/الدفع (ADR-010a).
- كل المبالغ `decimal` عبر `bcmath` — يُمنع `float` (المبدأ 6، ADR-001).

### الإشعارات
- إشعار المشتريات/المورد عند سداد فاتورة.
- إشعار العميل بإيصال دفع/استرداد.
- تنبيه المدير العام بتقارير مالية دورية.

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| محاولة حذف قيد معتمد | رفض — يُعكَس بقيد عكسي (ADR-016). |
| قيد غير متوازن | رفض الترحيل. |
| دفع يتجاوز الفاتورة | رفض. |
| اعتراف مبكر بالإيراد | ممنوع قبل `delivered` (ADR-010a). |

### النتيجة النهائية
دفاتر متوازنة قابلة للتدقيق، فواتير ومدفوعات محدّثة الحالة، وتقارير مالية دقيقة — مع مبدأ العكس لا الحذف محفوظًا.

# 8. رحلة المسوّق (Marketer / Affiliate — مسوّق)

**الدور:** `affiliate`. **الصلاحيات المزروعة:** `dashboard.view, affiliate.view` (+ ⏳ `affiliate.manage` للعمليات الموسّعة). **المرحلة:** وحدة Affiliate (بعد Phase 3). العمولات محكومة بـ ADR-012.

### نقطة البداية
تسجيل كمسوّق واعتماده من الإدارة؛ الدخول إلى لوحة المسوّق الخاصة.

### الخطوات
1. التسجيل كمسوّق → اعتماد إداري (مطلوب قبل التفعيل).
2. الحصول على كود/رابط إحالة فريد (`?ref={code}`) لكل منتج/حملة.
3. مشاركة الروابط؛ يتتبّع النظام النقرات والتحويلات والطلبات المنسوبة.
4. عند إنشاء طلب منسوب: تُسجَّل عمولة `expected` (تقديرية — ADR-012a).
5. عند `delivered`: تنتقل العمولة إلى `earned` (بعد التسليم فقط — ADR-012 طريقة 8).
6. بعد الموافقة الإدارية → `approved` → `payable`.
7. طلب سحب من المحفظة (Wallet) → بعد الدفع → `paid`.

### الصلاحيات
- `affiliate.view` لرؤية **محفظته وطلباته المنسوبة فقط** (Policy) — لا وصول لبيانات مسوّقين آخرين ولا للوحة الإدارة.
- **لا يرى التكلفة ولا `average_cost` ولا هوامش المنتجات** (ADR-013). أساس عمولته قد يكون فرق السعر (`sale_price − marketer_price`) دون كشف التكلفة (ADR-006/012).

### تحقّقات النظام
- **أساس العمولة (ADR-012c):** صافي قيمة البند بعد الخصم و**قبل** رسوم الشحن/الدفع (قابل للإعداد `commission.base`).
- **الاستحقاق بعد التسليم فقط:** لا `earned` قبل `delivered` (ADR-012).
- **الأثر العكسي (ADR-012b):** إلغاء قبل التسليم → `cancelled`؛ إرجاع كامل بعد الاستحقاق → `reversed`؛ إرجaع جزئي → تخفيض تناسبي.
- منع سحب يتجاوز الرصيد `payable` في المحفظة.
- منع نسب عمولة مزدوجة لنفس الطلب (كشف تكرار الإحالة).

### الإشعارات
- إشعار المسوّق عند: قبول التسجيل، طلب منسوب جديد (`expected`)، استحقاق عمولة (`earned`)، اعتماد (`approved`)، ودفع (`paid`).
- تنبيه للمدير/المحاسب بطلبات السحب المعلّقة.
- إشعار عكس العمولة عند إرجاع (`reversed`).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| سحب يتجاوز الرصيد | رفض. |
| إرجاع طلب بعد استحقاق العمولة | عكس `reversed`/تخفيض تناسبي (ADR-012b). |
| محاولة رؤية التكلفة | حجب (ADR-013). |
| إحالة مكرّرة لنفس الطلب | كشف ومنع. |

### النتيجة النهائية
مسوّق يتتبّع أداءه وعمولاته عبر دورة `expected → earned → approved → payable → paid`، مع محفظة دقيقة ومعالجة صحيحة للإرجاع/الإلغاء.

# 9. رحلة مندوب التوصيل (Delivery Employee — مندوب توصيل)

**الدور:** ⏳ غير مزروع بعد؛ يُشتق من `orders.view` + صلاحية تحديث الشحن (⏳ مقترح `orders.updateShipment`/`delivery.manage`). **المرحلة:** Phase 3 (الشحن والتسليم).

### نقطة البداية
لوحة/تطبيق التوصيل (عبر `/api/v1` — المبدأ 11): قائمة الطلبات `ready_to_ship`/`out_for_delivery` المسندة إليه.

### الخطوات
1. استلام قائمة الطلبات الجاهزة للتوصيل مع العناوين (area/city — ADR-014) وبيانات التواصل.
2. تحديث الحالة إلى `out_for_delivery` عند الخروج للتوصيل (ADR-010).
3. التواصل مع العميل عند الاقتراب (WhatsApp/SMS عبر `MessagingContract`).
4. عند النجاح: تحديث الطلب إلى `delivered` وحالة الشحن إلى `delivered`، وتسجيل تحصيل الدفع عند الاستلام (COD) إن وُجد.
5. عند التعذّر: `customer_unavailable` أو `delivery_failed`، أو `delayed` مع إعادة جدولة.

### الصلاحيات
- رؤية **الطلبات المسندة إليه فقط** (Policy) — لا وصول لكامل قائمة الطلبات ولا للأسعار/التكلفة/الهوامش (ADR-013).
- صلاحية محصورة بانتقالات الشحن (`out_for_delivery`, `delivered`, `delivery_failed`, `customer_unavailable`) — لا `orders.manage` الكامل.

### تحقّقات النظام
- انتقالات الحالة القانونية فقط (State Machine — ADR-017): لا يمكن القفز إلى `delivered` من حالة غير مؤهّلة.
- **الاعتراف بالإيراد وخصم COGS مرتبط بـ `shipped`/`delivered`** (ADR-009/010a) — لا يعبث المندوب بالمخزون مباشرة.
- تسجيل تحصيل COD ضمن معاملة (المبدأ 7) وربطه بحالة الدفع (`paid`).
- كل تحديث حالة يُدقَّق مع الموقع/الوقت (المبدأ 8).

### الإشعارات
- إشعار العميل عند `out_for_delivery` و`delivered` (WhatsApp/SMS).
- تنبيه المبيعات/الخدمة عند `delivery_failed`/`customer_unavailable` للمتابعة.
- إشعار المحاسب بتحصيل COD.

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| العميل غير متاح | `customer_unavailable` + إعادة جدولة/تنبيه المبيعات. |
| رفض الاستلام | `delivery_failed` → مسار إرجاع (ADR-011). |
| انتقال حالة غير قانوني | رفض (State Machine). |
| تحصيل COD فاشل | إبقاء الدفع `unpaid` + تنبيه. |

### النتيجة النهائية
طلب `delivered` مع تحصيل مؤكّد (إن وُجد)، يُطلق الاعتراف بالإيراد (ADR-010a) واستحقاق عمولة المسوّق (`earned` — ADR-012)، أو مسار فشل/إرجاع موثّق.

# 10. رحلة المدير العام (General Manager — المدير العام)

**الدور:** `manager` (بصلاحيات إشرافية موسّعة؛ قد يُمنح `pricing.view_cost` و`reports.view` كاملة). **المرحلة:** عبر كل المراحل (إشراف).

### نقطة البداية
لوحة قيادة تنفيذية (Executive Dashboard) تجمّع مؤشرات كل الوحدات.

### الخطوات
1. مراجعة KPIs الموحّدة: مبيعات، مخزون، مشتريات، مالية، تسويق (المتطلب 2.11).
2. اعتماد القرارات عالية الأثر: أوامر شراء كبيرة، تجاوزات الأسعار، سياسات الخصم.
3. مراقبة الربحية (بشرط `pricing.view_cost` — ADR-013) وهوامش المنتجات مقابل `target_margin`.
4. مراجعة سجل التدقيق (`audit.view`) للعمليات الحسّاسة عبر الوحدات (المبدأ 8).
5. تحليل أداء الفروع/المستودعات (جاهزية تعدد الفروع — المبدأ 1) والمسوّقين.
6. تصدير التقارير التنفيذية (PDF/Excel).

### الصلاحيات
- إشراف واسع عبر `reports.view` + `audit.view` + صلاحيات الاعتماد.
- **`pricing.view_cost`** (⏳ مقترح) يُمنح صراحةً للمدير العام لرؤية الربحية والتكلفة (ADR-013) — لا يُفترض تلقائيًا.
- الموافقات عالية الأثر عبر سير موافقات موثّق (APPROVAL_WORKFLOWS).

### تحقّقات النظام
- كل موافقة/تجاوز يُسجَّل في التدقيق مع القيمة قبل/بعد (المبدأ 8).
- التقارير مبنية على بيانات append-only (دفتر المخزون/القيود) — لا تلاعب رجعي (ADR-008/016).
- احترام حدود الأسعار الصلبة حتى مع صلاحية المدير (ADR-006a).

### الإشعارات
- تنبيهات استثنائية: انخفاض مخزون حرج، انخفاض هامش دون `target_margin`، طلبات اعتماد كبيرة.
- ملخّصات تنفيذية دورية (Email).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| رؤية الربحية بلا `pricing.view_cost` | حجب حتى تُمنح الصلاحية (ADR-013). |
| موافقة تكسر حدًا صلبًا | رفض النظام (ADR-006a). |
| اعتماد بلا سير موافقة | منع — كل اعتماد موثّق. |

### النتيجة النهائية
رؤية تنفيذية شاملة موثّقة بالتدقيق، قرارات معتمدة ضمن الضوابط، وربحية مراقبة عبر كل الوحدات والفروع.

# 11. رحلة مدير النظام (System Administrator — مدير النظام)

**الدور:** `admin` (كل الصلاحيات `*`). **المرحلة:** Phase 1 (منجزة) وتمتد لكل المراحل.

### نقطة البداية
لوحة الإدارة الكاملة بعد الدخول كـ `admin@tawfeer.online` (بيانات تطوير فقط).

### الخطوات
1. إدارة المستخدمين والأدوار والصلاحيات (`users.*`, `roles.manage`) — RBAC لا أسماء (المبدأ 12).
2. إدارة الفروع (`branches.manage`) والمستودعات (جاهزية تعدد الفروع/المستودعات — المبدآن 1/2).
3. ضبط الإعدادات الديناميكية (`settings.manage`): العملة (`SAR` افتراضي)، الضريبة (`tax.rate=15%`)، الشحن، اللغة، الحدود — مع cache وإبطاله عند التحديث (المبدأ 9، ADR-001/015).
4. إدارة الحالات القابلة للإدارة (`statuses.manage`): طلب/دفع/شحن + المفاتيح القانونية (المبدأ 10، ADR-017).
5. مراجعة سجل التدقيق الكامل (`audit.view`) — append-only (المبدأ 8).
6. إدارة طبقة التكامل: تفعيل/تبديل Drivers للدفع والرسائل خلف العقود (المبدأ 13، ADR-019) دون لمس منطق الأعمال.
7. إدارة الوحدات المستقلة وإعداداتها (المبدأ 14).

### الصلاحيات
- **كل الصلاحيات** (`admin => ['*']`) بما فيها `pricing.view_cost`/`pricing.override_min_price` (⏳ عند زرعها).
- الوحيد القادر على تعديل بنية الأدوار والإعدادات الحسّاسة.

### تحقّقات النظام
- منع أي شرط قائم على اسم/إيميل مستخدم (`if email === ...` ممنوع — المبدأ 12).
- تعديل الإعدادات يبطل الـ cache فورًا (المبدأ 9).
- عدم كسر الفرادة المركّبة الجاهزة لتعدد المستأجرين عند التعديل (المبدأ 3، ADR-004).
- كل تغيير إداري يُدقَّق (المبدأ 8) — حتى الأدمن غير معفى.
- الحفاظ على المفاتيح القانونية للحالات (لا اختراع مفتاح خارج القوائم دون تحديث DECISIONS.md).

### الإشعارات
- تنبيهات أمنية: تسجيل دخول مشبوه، تغيّر صلاحيات، تبديل Driver دفع/رسائل.
- إشعارات النظام: فشل طوابير، حالة النسخ الاحتياطي (المتطلب غير الوظيفي — الموثوقية).

### حالات الفشل الممكنة
| الفشل | استجابة النظام |
|------|----------------|
| حذف آخر مستخدم أدمن | منع (ضمان وجود مدير). |
| مفتاح حالة خارج القائمة القانونية | رفض حتى تحديث DECISIONS.md أولًا. |
| تعطيل حالة افتراضية مستخدمة | منع/تحذير (سلامة State Machine). |
| تبديل Driver بإعداد ناقص | رفض التفعيل + إبقاء الـ NullDriver. |

### النتيجة النهائية
نظام مُدار بالكامل: مستخدمون وأدوار وإعدادات وحالات وتكاملات مضبوطة، مع أثر تدقيق شامل وبنية جاهزة للتوسّع (فروع/مستودعات/مستأجرون).

## أسئلة مفتوحة (Open Questions)

1. **دور «مشتريات» و«توصيل»:** غير مزروعَين في `RolePermissionSeeder`؛ يُشتقان حاليًا من صلاحيات (`purchasing.*`، وصلاحية شحن مقترحة). هل نزرع دورين مخصّصين في Phase 2/3؟
2. **صلاحيات الأسعار:** `pricing.view_cost` و`pricing.override_min_price` معرّفتان في ADR-006/013 لكن غير مزروعتين بعد — تُضافان عند Phase 2/3. لمن تُمنح `pricing.view_cost` افتراضيًا (المدير العام فقط؟).
3. **توسيع حالات الطلب:** بذور Phase 1 مبسّطة مقابل ADR-010 الكاملة — يُعتمد توقيت التوسيع في بداية Phase 3.
