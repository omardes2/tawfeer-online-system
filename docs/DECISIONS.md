## ADR-000 — تنسيق القرارات
كل قرار: **السياق → القرار → البدائل المرفوضة → الأثر**. القرارات المرقّمة نهائية ما لم تُراجَع صراحةً.

## ADR-001 — العملة والمبالغ (Money)
- **القرار:** كل الأسعار وقيم المبيعات `decimal(15,2)`. التكاليف وأوزان المتوسط المرجّح `decimal(15,4)` (دقّة أعلى تفاديًا لتراكم أخطاء التقريب). الكميات `decimal(15,3)`.
- **يُمنع** `float`/`double` (المبدأ 6). الحساب في PHP عبر `bcmath`.
- **عملة أساسية واحدة** للنظام (من الإعدادات، الافتراضي `SAR`). جدول `currencies` يُخزّن العملات وأسعار الصرف للعرض/المستقبل، لكن **الدفاتر تُمسك بالعملة الأساسية** في Phase 2/3.

## ADR-002 — المعرّفات (Identifiers)
- مفتاح داخلي `id` BIGINT، ومعرّف خارجي `uuid` لكل كيان **يُكشف عبر API/روابط** (المبدأ 4): المنتجات، الطلبات (لاحقًا)، الموردون، المستودعات، أوامر الشراء.
- الكيانات المرجعية الداخلية البحتة (المدن، الوحدات، السمات) **قد تكتفي بـ id** إن لم تُكشف خارجيًا؛ لكن الافتراضي إضافة `uuid` لأي كيان قد يظهر في API عام.
- **أرقام الأعمال المقروءة (Human numbers):** تُولّد بنمط مُهيّأ من الإعدادات:
  - أمر شراء: `PO-{YYYY}-{seq}` — مثال `PO-2026-000042`.
  - طلب (Phase 3): `ORD-{YYYY}-{seq}`.
  - تحويل مخزون: `TRF-{YYYY}-{seq}`. تسوية جرد: `ADJ-{YYYY}-{seq}`.
  - التسلسل لكل (نوع × سنة)، ويُولّد داخل معاملة مع قفل لتفادي التكرار.

## ADR-003 — تعدد الفروع/المستودعات (Multi-Branch / Multi-Warehouse)
- **الفرع (Branch)** وحدة تنظيمية؛ **المستودع (Warehouse)** موقع مادّي للمخزون. مستودع واحد يتبع فرعًا واحدًا، والفرع قد يملك عدة مستودعات.
- المخزون يُمسك دائمًا **لكل (متغيّر × مستودع)** — لا رصيد عام (المبدأ 2).
- كل كيان تشغيلي يحمل `branch_id` (يُملأ بالفرع الافتراضي الآن). لا قيم ثابتة `branch_id=1`.

## ADR-004 — جاهزية تعدد الشركات (Multi-Company / Multi-Tenant)
- **القرار:** لا `company_id`/`tenant_id` فعلي في Phase 2 (المبدأ 3). لكن:
  - لا مفاتيح فريدة **عامة** تمنع إضافته لاحقًا؛ نستخدم **فرادة مركّبة** حيثما لزم (مثال: SKU فريد ضمن نطاق الشركة مستقبلًا → الآن فريد عام مع ملاحظة الترقية).
  - كل الاستعلامات تمرّ عبر طبقات (Models/Services) تسمح بحقن Scope لاحقًا في مكان واحد.
- **الأثر:** ترقية تعدد الشركات = إضافة عمود + Global Scope، دون إعادة تصميم.

## ADR-005 — نموذج التكلفة (Costing) = المتوسط المرجّح (Weighted Average Cost)
- **القرار:** تقييم المخزون بطريقة **المتوسط المرجّح المتحرّك (Moving Weighted Average, WAC)** لكل (متغيّر × مستودع) — أو على مستوى الشركة حسب إعداد `inventory.costing_scope` (افتراضي: لكل مستودع).
- عند كل استلام: `WAC_جديد = (قيمة المخزون الحالية + التكلفة المُحمّلة للوارد) / (الكمية الحالية + الكمية الواردة)`.
- **التكلفة المُحمّلة (Landed Cost):** تكلفة الشراء + توزيع مصاريف الشحن/الاستيراد/الجمارك على الأصناف (حسب القيمة أو الوزن أو الكمية — `purchasing.landed_allocation`).
- **تكلفة البضاعة المباعة (COGS):** تُحتسب بـ WAC وقت **خصم المخزون النهائي** (الشحن).
- **البدائل المرفوضة:** FIFO/LIFO (أعقد ولا يطلبه العمل الآن)، سعر ثابت (غير دقيق للربحية).
- **الأثر:** حقول `cost_price` (آخر شراء) و`average_cost` (WAC) على مستوى المخزون؛ التغيّرات تُدوّن في دفتر المخزون.

## ADR-006 — طبقات الأسعار (Price Tiers)
لكل منتج/متغيّر مجموعة أسعار مُدارة:
| الحقل | المعنى | ملاحظة |
|------|--------|--------|
| `cost_price` | تكلفة آخر شراء | مرجعي |
| `average_cost` | المتوسط المرجّح | يُحتسب آليًا |
| `retail_price` | سعر التجزئة | البيع للعميل النهائي |
| `wholesale_price` | سعر الجملة | للعملاء بالجملة |
| `marketer_price` | سعر أساس المسوّق | أساس عمولة الفرق |
| `min_price` | أدنى سعر بيع مسموح | **حد صارم** |
| `promo_price` | سعر ترويجي مؤقت | ضمن فترة |
- **الحد الأدنى (ADR-006a):** يُمنع البيع تحت `min_price` إلا بصلاحية `pricing.override_min_price` **وبموافقة** (APPROVAL_WORKFLOWS). أي محاولة تُسجَّل في التدقيق.
- **هامش الربح المستهدف (`target_margin`)** يُخزّن للتنبيه فقط، لا يمنع.

## ADR-007 — دلاء المخزون (Stock Buckets)
كمية المخزون تُفكَّك إلى دلاء منفصلة لكل (متغيّر × مستودع):
| الدلو | المعنى |
|------|--------|
| `on_hand` | الموجود ماديًا |
| `reserved` | محجوز لطلبات مؤكّدة |
| `available` | `on_hand − reserved` (محسوب) |
| `damaged` | تالف (خارج البيع) |
| `returned_pending` | مرتجع بانتظار الفحص |
| `in_transit` | قيد التحويل بين المستودعات |
- **المتاح للبيع = `on_hand − reserved`**. الدلاء `damaged`/`returned_pending`/`in_transit` **لا** تُحتسب متاحة.
- **منع السالب (ADR-007a):** يُمنع أن يصبح `available` سالبًا إلا إذا فُعِّل `inventory.allow_negative` (لكل مستودع). كل حركة تُتحقّق داخل معاملة مع قفل صف المخزون (المبدأ 7).

## ADR-008 — دفتر المخزون وحركاته (Inventory Ledger vs Movements)
- **`inventory_movements`:** سجلّ الأحداث الخام (وارد/صادر/تحويل/تسوية/حجز/تحرير) — نيّة الحركة.
- **`inventory_ledger`:** دفتر **append-only** لكل تغيّر في الكمية والتكلفة (رصيد جارٍ + WAC بعد كل حركة) — للتتبّع والتدقيق والتقارير. لا Soft Delete، لا تعديل.
- كل حركة مخزون تُنتج قيدًا/أكثر في الدفتر داخل نفس المعاملة.

## ADR-009 — توقيت المخزون في دورة الطلب (Phase 3 — يُصمَّم الآن)
هذه قرارات تُلزم تصميم Phase 2 (بنية الحجز) وتُنفَّذ في Phase 3:
| اللحظة | الأثر على المخزون |
|--------|-------------------|
| تأكيد الطلب (`confirmed`) → `stock_reserved` | **حجز**: `reserved += qty` (لا يمسّ `on_hand`). عبر `stock_reservations`. |
| الشحن (`shipped`) | **خصم نهائي**: `on_hand -= qty`, `reserved -= qty`، وتُحتسب COGS بـ WAC. |
| الإلغاء قبل الشحن | **تحرير**: `reserved -= qty`. |
| الإلغاء/الفشل بعد الشحن | يعالَج كإرجاع (ADR-011). |
| الإرجاع المقبول والمفحوص | إمّا `on_hand += qty` (صالح) أو `damaged += qty` (تالف). |
- الحجز **قابل للإعداد** (`inventory.reserve_on`: `confirmed`|`paid`)، الافتراضي `confirmed`.

## ADR-010 — دورة حياة الطلب (Order Lifecycle — Phase 3، مُعرّفة الآن)
الحالات القانونية (تمتد الحالات المزروعة في الأساس):
`draft → new → awaiting_contact → awaiting_confirmation → confirmed → stock_reserved → preparing → ready_to_ship → shipped → out_for_delivery → delivered`
وحالات فرعية/نهائية: `delayed`, `customer_unavailable`, `cancelled`, `delivery_failed`, `returned`, `partially_returned`, `exchanged`.
- **نهائية (is_final):** `delivered`(قبل نافذة الإرجاع)، `cancelled`، `returned`، `exchanged`.
- **الاعتراف بالإيراد (ADR-010a):** عند `delivered` (أساس الاستحقاق) — لا عند الإنشاء ولا الدفع.
- **قابلية التعديل:** الطلب قابل للتعديل الكامل حتى `confirmed`؛ بعد الحجز تُقيَّد التعديلات (الكميات تتطلب إعادة حجز)؛ بعد `shipped` تُمنع تعديلات البنود (إلا عبر إرجاع/استبدال).
- **من يغيّر ماذا:** مصفوفة الانتقالات في `APPROVAL_WORKFLOWS.md` (ملكية كل انتقال حسب الدور/الصلاحية — المبدأ 12).
- **مصدر الطلب (`channel`/`source`):** `web` | `manual` (موظف) | `marketer` | `pos`(لاحقًا). طلبات الموظف اليدوية تبدأ من `new`/`draft` وقد تتجاوز `awaiting_contact`.

## ADR-011 — المرتجعات والاستبدال (Returns)
- تدفّق: `return_request → approved → received → inspected → (restock | to_damaged) → (refund | exchange | credit_note)`.
- **الأثر العكسي (Reversal):** الإرجاع **يعكس** الإيراد وCOGS والمخزون والعمولة (نسبيًا للكمية المرتجعة). المرتجع الجزئي يعالَج على مستوى البند/الكمية.
- **لا حذف — بل عكس (المبدأ + ADR-016):** لا تُحذف حركة مالية/مخزونية معتمدة؛ تُنشأ حركة عكسية.

## ADR-041 — فاتورة الشراء بخطوة واحدة (ADR-041)

- **الحفظ = ترحيل فوري:** زر واحد «حفظ» يُنشئ الفاتورة ويعتمدها ويُرحّلها محاسبيًا ويُدخل البضاعة للمخزون داخل **معاملة واحدة** (`createAndPost`) — بلا مسودّة/اعتماد منفصلين (قرار إداري). فشل أي خطوة يلغي الكل فلا تبقى فاتورة معلّقة.
- **تعديل فاتورة مُرحّلة (`updatePosted`):** يعكس أثر المخزون القديم (`purchaseReturn`)، يستبدل البنود، يُدخل الكميات/التكاليف الجديدة، ثم **يُحدّث القيد المحاسبي في مكانه** (`replaceLines` — نفس رقم القيد) — مطابقًا لسياسة فواتير المبيعات.
- **حذف فاتورة مُرحّلة (`deletePosted`):** يسحب البضاعة المُدخَلة ويحذف القيد المحاسبي المرتبط (لا عكس) ثم يحذف الفاتورة — مطابقًا لسياسة حذف فاتورة المبيعات.
- **حماية:** الفاتورة التي سُدّد منها أي مبلغ **لا تُعدَّل ولا تُحذف** حتى تُعكس دفعاتها (وإلا اختلّت الخزينة وذمم المورد). وإن كانت البضاعة قد بيعت ولم تعُد متاحة، يفشل السحب برسالة واضحة بدل إفساد رصيد المخزون.

## ADR-012 — نموذج العمولة (Commission Model)
طرق مدعومة (لكل منتج/حملة/مسوّق حسب قاعدة `commission_rules`):
1. مبلغ ثابت لكل منتج. 2. نسبة من المبيعات. 3. نسبة من الربح. 4. **فرق السعر** (سعر البيع − `marketer_price`). 5. متدرّجة شهريًا (Tiers). 6. حسب المنتج. 7. حسب الحملة. 8. **بعد التسليم فقط**.
- **حالات العمولة (ADR-012a):** `expected → pending → earned → approved → payable → paid` + `cancelled`, `reversed`.
  - `expected`: عند إنشاء الطلب (تقديري). `earned`: عند `delivered`. `approved`: موافقة إدارية. `payable`: مستحقة السحب. `paid`: بعد الدفع.
- **الأثر عند الإلغاء/الإرجاع (ADR-012b):** إلغاء قبل التسليم → `cancelled`. إرجاع كامل بعد الاستحقاق → `reversed`. إرجاع جزئي → تخفيض تناسبي.
- **الأساس (ADR-012c):** العمولة تُحتسب على **صافي قيمة البند بعد الخصم**، و**قبل** رسوم الشحن/الدفع (قابل للإعداد `commission.base`: `net_item`|`gross`|`profit`). رسوم التوصيل والدفع **لا** تُدرج افتراضيًا.

## ADR-013 — رؤية التكلفة للموظفين (Cost Visibility)
- سعر التكلفة و`average_cost` و`min_price` **لا تظهر** لموظف المبيعات إلا بصلاحية صريحة `pricing.view_cost` (المبدأ 12). التقارير الربحية محجوبة بلا الصلاحية.

## ADR-014 — الجغرافيا والشحن (Geography)
- تسلسل: **المحافظة (governorate) → المدينة (city) → المنطقة (area)**. **منطقة الشحن (shipping_zone)** تجميعة تسعير/تغطية تُربط بمدن/مناطق (علاقة كثير-لكثير)، مستقلة عن التسلسل الإداري.
- عنوان العميل (Phase 3) يشير إلى area/city/governorate. تكلفة الشحن تُشتق من `shipping_zone` (Phase 3).

## ADR-015 — الضرائب (Taxes)
- جدول `taxes` (اسم، نسبة، نوع شامل/مضاف، فعّال). المنتج قد يشير إلى ضريبة، وإلا الافتراضي من الإعدادات (`tax.rate=15%`, `tax.enabled`). حساب الضريبة فعلي في Phase 3.

## ADR-016 — الأثر المحاسبي (Accounting Hooks — لا تنفيذ الآن)
- المحاسبة **قيد مزدوج** (Double-Entry) تُنفَّذ في Phase 5، لكن كل حدث مالي في Phase 2/3 يُصمَّم لينتج **قيدًا لاحقًا** عبر أحداث (EVENTS): استلام بضاعة، تسوية مخزون، فاتورة مبيعات، تحصيل، دفع مورد، عمولة، إرجاع.
- **العكس لا الحذف:** كل معاملة معتمدة تُعكَس بقيد عكسي.

## ADR-017 — الحالات كبيانات لا Enum (Statuses)
- كل الحالات (طلب/دفع/شحن/عمولة/إرجاع/أمر شراء/استلام) في **جداول قابلة للإدارة** (المبدأ 10)، ذات `key` ثابت يعتمد عليه الكود، و`name` قابل للترجمة. المنطق (State Machine) يقرأ الانتقالات المسموحة من قاعدة البيانات/التهيئة.

## ADR-018 — الأحداث والطوابير (Events & Queues)
- كل عملية جوهرية تُطلق **حدث دومين (Domain Event)** (EVENTS.md). المستمعون الثقيلون (إشعارات، تقارير، فهرسة) يعملون في **طوابير** (المبدأ 11/13). لا منطق أعمال حرج داخل مستمع غير متزامن (الحرج داخل المعاملة).

## ADR-019 — API-First والعقود (Contracts)
- كل قدرة تُكشف عبر **REST API مُصدَّر `/api/v1`** باستجابات Resources موحّدة (المبدأ 11). أي مزوّد خارجي (شحن، دفع، رسائل) خلف **عقد (Interface)** + Driver (المبدأ 13).

## ADR-020 — التدقيق والحذف الناعم (Audit & Soft Delete)
- الكيانات الرئيسية: **Soft Delete** (المبدأ 5). الدفاتر (`inventory_ledger`, `audit_logs`, journal lines لاحقًا): **append-only بلا Soft Delete**.
- الكيانات الحسّاسة تحمل تريتة `Auditable` (المبدأ 8): المنتجات، الأسعار، المخزون، الموردون، أوامر الشراء، التحويلات، التسويات.

## المفردات القانونية (Canonical Vocabularies)

> **قاعدة إلزامية:** لا يجوز لأي وثيقة أو كود اختراع مفتاح حالة خارج هذه القوائم دون تحديثها هنا أولًا.

### حالات أمر الشراء (Purchase Order)
`draft → pending_approval → approved → partially_received → received → closed` + `cancelled`.

### حالات فاتورة المورد (Supplier Invoice — Phase 4)
`draft → pending_approval → approved → partially_paid → paid` + `cancelled` (يُعكَس لا يُحذف).

### حالات المخزون-الحركة (Movement Types)
`purchase_in` · `sale_out` · `transfer_out` · `transfer_in` · `adjustment_in` · `adjustment_out` · `reserve` · `release` · `return_in` · `damage_out` · `purchase_return_out` (مُضاف — ADR-025).

### حالات الطلب / الدفع / الشحن / العمولة / الإرجاع
معرّفة في ADR-010 / الأساس / ADR-009 / ADR-012 / ADR-011 على التوالي.

### حالة التوصيل القانونية (Canonical Delivery Lifecycle — ADR-038، Phase 4.3)
`draft → ready_for_pickup → picked_up → { on_hold ⇄ picked_up } → delivered_cod_held → funds_at_courier_accounting → closed`
ومسار الإرجاع: `picked_up|on_hold → returning_to_courier → return_in_transit → closed`؛ والإلغاء `cancelled` (قبل الاستلام فقط).
> **منفصلة تمامًا عن حالة المزوّد الخام** (`provider_status`)؛ التعيين مزوّد ← قانوني يقع في الـDriver (لا في وحدات الأعمال). `closed` هي **نقطة الاكتمال المالي الوحيدة** (تسوية الطلب + استحقاق العمولات `eligible`). أسباب التعليق المُصنّفة: `customer_no_answer · wrong_phone · wrong_address · customer_requested_delay · customer_refused · area_unavailable · courier_issue · business_issue · other`.

### حالات تحويل المستودعات (Warehouse Transfer) — مُرسّمة في مراجعة التصميم
`draft → pending_approval → approved → dispatched(in_transit) → received` + `cancelled`.
> `dispatched` يحرّك الكمية إلى دلو `in_transit` (ADR-007)؛ `received` يودعها في مستودع الوجهة. توقيعان منفصلان (إرسال/استلام).

### حالات تسوية الجرد (Stock Adjustment) — مُرسّمة (متوافقة مع §26)
`draft → pending_approval → approved → posted` + `cancelled`.
> `approved` اعتماد إداري (لا أثر على المخزون بعد)؛ `posted` يطبّق الأثر: حركات `adjustment_in`/`adjustment_out` + قيود دفتر، داخل معاملة. لا حذف بعد `posted` (عكس فقط — ADR-016).

### حالات حجز المخزون (Stock Reservation) — مُرسّمة (متوافقة مع §25)
`active → released` | `active → consumed` | `active → expired`.
> `active` = محجوز (`reserved`)؛ `consumed` عند الشحن (خصم نهائي — Phase 3)؛ `released`/`expired` يعيدان الكمية للمتاح (ADR-009).

## ADR-021 — تسمية الصلاحيات (Permission Naming) [مُعتمد في مراجعة التصميم]
- **السياق:** أنتجت وثائق التصميم مخططًا دقيقًا `{module}.{resource}.{action}` (مثل `catalog.products.view`, `inventory.transfer.approve`) بينما زرعت Phase 1 مجموعة **أخشن** من 27 صلاحية (`catalog.view`, `inventory.manage`...).
- **القرار:** المخطط الدقيق **`{module}.{resource}.{action}`** هو **القانوني** للنظام. صلاحيات Phase 1 الأخشن تبقى كـ **مجموعات/أسماء مستعارة انتقالية** تُوسَّع إلى الصلاحيات الدقيقة **عند بناء كل وحدة** (تُضاف عبر seed لكل مرحلة). لا يُعتمد على أي صلاحية أخشن في كود جديد.
- **صلاحيات حسّاسة مُرسّمة:** `pricing.view_cost` (رؤية التكلفة/الربح — ADR-013)، `pricing.override_min_price` (تجاوز أدنى سعر — ADR-006a)، `reports.view_financial` (تقارير الربحية). تُزرع مع وحداتها.
- **الأثر:** تحديث `RolePermissionSeeder` تدريجيًا لكل وحدة؛ الأدوار السبعة تبقى ثابتة (المبدأ 12).

## ADR-023 — توسعة حقول المنتج الكتالوجي (Product Catalog Fields) [مُعتمد في Phase 2.3]
- **السياق:** يتطلّب المالك في Phase 2.3 حقولًا تتجاوز `products` §16: تسمية/وصف **ثنائيا اللغة**، **حالة تحريرية** (draft/active/archived)، **ظهور** (visible/hidden)، **مميّز (featured)**، **ترتيب**، **حقول SEO**، و**بيانات بحث**.
- **القرار:** إضافة هذه الأعمدة إلى `products` دون المساس بأعمدة التصميم §16:
  - `name_en`, `short_description_en`, `description_en` (إنجليزي ثانوي؛ العربي أساسي).
  - `status` (`draft` افتراضي / `active` / `archived`) — دورة الحياة التحريرية.
  - `visibility` (`visible` افتراضي / `hidden`) — ظهور المتجر.
  - `is_featured` (bool)، `sort_order` (int)، `meta_title`/`meta_description`/`meta_keywords` (SEO)، `search_keywords` (بيانات بحث).
- **`is_active` (من §16) يبقى** ويُشتقّ آليًا من الحالة: `is_active = (status === 'active')` — تحافظ عليه `ProductService` ليخدم فهرس `(is_active, type)` واستعلامات المتجر السريعة.
- **الأسعار (§16):** الأعمدة موجودة للوفاء بالتصميم، لكن **لا محرّك تسعير في Phase 2.3** (تُترك بقيمها الافتراضية ولا تُدار في نماذج هذه المرحلة). حقول التكلفة محجوبة بـ `pricing.view_cost` (ADR-013).
- **FK مؤجّلة:** `tax_id` (جدول taxes غير مُنشأ)، و`product_images.variant_id` (المتغيّرات غير مُنشأة) — أعمدة nullable بلا قيد الآن، تُربط في مرحلتها.
- **الأثر:** لا إعادة تصميم؛ إضافة أعمدة فقط تتبع كل الأعراف (uuid، soft-delete، auditable، RBAC).

## ADR-025 — تفصيل مخطط المشتريات (Purchasing Schema Detail) [مُعتمد في Phase 2.5]
- **السياق:** `PHASE_2_DESIGN` يفصّل الموردين وجهات الاتصال (§9/§10) فقط؛ أوامر الشراء والاستلام والمرتجعات موصوفة عاليًا في `DATABASE_DESIGN §4` + `BR-PUR`. هذا الـADR يثبّت تفصيلها متّبعًا كل الأعراف (لا إعادة تصميم).
- **الكيانات:** `purchase_orders` (+`purchase_order_items`)، `goods_receipts` (+`goods_receipt_items`)، `supplier_returns` (+`supplier_return_items`). كلها: رأس بـ uuid + soft-delete + Auditable؛ البنود بلا uuid/soft-delete.
- **الترقيم (ADR-002):** `PO-{YYYY}-{seq}` · `GRN-{YYYY}-{seq}` · `PRET-{YYYY}-{seq}`.
- **حالات الاستلام (GRN):** `draft → posted` + `cancelled`. الترحيل يطبّق `purchase_in` عبر `InventoryService` (BR-PUR-04).
- **حالات مرتجع المشتريات:** `draft → approved → posted` + `cancelled`. الترحيل يطبّق حركة صادرة.
- **نوع حركة جديد `purchase_return_out`:** مرتجع المشتريات صادر يخفّض `on_hand` (BR-PUR-11)؛ أُضيف إلى مفردات ADR-008 (لم تكن تغطّي مرتجع المورد صراحةً). يُخصم بتكلفة WAC الحالية.
- **التكامل مع المخزون (إلزامي):** الاستلام والمرتجع **يمرّان حصريًا عبر `InventoryService`** (لا تحديث مباشر لجداول المخزون)، داخل معاملات ذرّية، ويكتبان حركة + قيد دفتر (BR-PUR-13).
- **التكلفة المُحمّلة (Landed Cost — BR-PUR-06):** `goods_receipts.additional_cost` تُوزَّع على البنود بنسبة قيمة السطر قبل احتساب WAC.
- **FK مؤجّلة:** `suppliers.governorate_id/city_id/currency_id` (جداولها غير مُنشأة) — أعمدة nullable بلا قيد الآن.

## ADR-055 — محتوى منشورات فيسبوك وإنستغرام [**أُزيل في Phase 7.7** — بقرار المالك؛ الشيفرة في تاريخ Git]
- **السياق:** طلب المالك صفحةً لإنشاء محتوى المنشورات. والبنية قائمة أصلًا — `AiContentService` بنوع `social_caption` وحدّ معدّل وسجلّ استخدام وتراجع رشيق — فالمرحلة واجهةٌ وسجلٌّ ورابط، لا طبقة ذكاءٍ جديدة.
- **يُولّد ويحفظ ولا ينشر.** النشر التلقائي يحتاج `pages_manage_posts` وواجهة نشر إنستغرام ومراجعة تطبيق، والأهمّ أنه يجعل خطأً في التوليد يظهر أمام الزبائن قبل أن يراه أحد. فالمخرَج نصٌّ يُنسخ، و«نُشر» علامةٌ يضعها إنسان. واختبارٌ يحرس أنه لا مسار في النظام ينشر إلى المنصّة.
- **الرابط متتبَّع دائمًا — وهذا هو المقصد لا التوليد.** منشورٌ برابطٍ عارٍ يبيع ولا يُعرَف أنه باع: يدخل طلبُه تحت «غير منسوب» فيبدو الإعلان المدفوع وحده هو الذي يعمل، ويُوقَف النشر العضويّ لأنه «بلا نتيجة». والوسم هنا هو نفسه الذي تقرأه نسبة الطلبات (ADR-054) — فالمنشور العضويّ والإعلان المدفوع يُقاسان بالمسطرة نفسها ويظهران في التقرير نفسه.
- **`utm_campaign=tw-ch-{id}` لا `utm_content`:** الثاني محجوز لمعرّف المجموعة الإعلانية، وحشوُ رمزٍ عضويّ فيه كان سيجعل النسبة تبحث عن مجموعةٍ لا وجود لها. والقناة تُتحقَّق من وجودها عند الحلّ — رمزٌ لقناةٍ محذوفة لا يُنسَب إليه شيء.
- **الرابط يُخزَّن مع المنشور ولا يُعاد بناؤه:** تغيّر الإعدادات لاحقًا كان سيُظهر رابطًا غير الذي وصل الزبائن فعلًا.
- **جدولٌ لا مولّد نصوصٍ عابر (`social_posts`):** المنشور يُعاد ويُعدَّل ويُقارَن بما سبقه — أيّ صنفٍ نُشر له ومتى، وما الذي لم يُنشر منذ شهر. وبلا سجلٍّ يبقى ذلك في ذاكرة صاحب العمل فيُعاد نشر الصنف نفسه ويُنسى غيره. و`ai_model`/`ai_status` مخزَّنان: نصٌّ ولّده نموذجٌ احتياطي بعد فشل المزوّد يختلف في جودته، ومن يقرأ المنشور بعد شهر يحتاج أن يعرف.
- **السعر ضمن مدخلات التوليد:** المنشور بلا سعرٍ يُنتج محادثاتٍ سؤالُها الأول «كم السعر؟» — وهي محادثاتٌ تُحسَب على الحملة ولا تتحوّل.
- **الصلاحيات:** `marketing.social.{view,manage}` للمدير العام والمدير معًا — لا تُنفق مالًا ولا تكشف تكلفة، وحصرُها في شخصٍ واحد يجعل الصفحة تُهجَر.
- **الاختبارات:** 8 اختبارات، أهمّها الحلقة كاملة: رابطٌ موسوم ← زيارة ← طلب ← نسبةٌ إلى الصفحة الصحيحة.

## ADR-054 — قياس الشراء ونسبة الطلب الإلكتروني إلى إعلانه [مُعتمد في Phase 7.5]
- **السياق:** قرّر المالك أن تُشغَّل حملات «الشراء عبر الموقع» على **حساب إعلاني آخر** غير حساب حملات الرسائل. وتبديلُ رقم الحساب وحده لا يكفي: النظام كلّه كان أعمى عن سؤالين لا حكم بدونهما — **هل رأت المنصّة الشراء؟** و**أيّ إعلانٍ أنتج هذا الطلب؟**
- **المنصّة لا تُحسِّن على ما لا تراه.** بلا حدث شراءٍ يصلها تختار جمهورًا **ينقر** لا جمهورًا **يشتري**، فتصرف الميزانية كاملةً وتبدو الحملة «تعمل». فالبكسل وConversions API ليسا تحسينًا اختياريًّا بل شرطُ الهدف نفسه.
- **حدث الشراء من الخادم لا من المتصفّح.** سببان: مانعات الإعلانات وiOS تُسقط جزءًا كبيرًا من أحداث المتصفّح، و**مسار الإتمام محميّ لا يُمسّ** (تكامل التوصيل) — فلا سطر في شيفرة الإتمام. يُرسَل من `Order::created` عبر مهمّة في الطابور: نداءٌ بطيء إلى المنصّة كان سيؤخّر تأكيد الطلب أمام الزبون أو يُفشله. **القياس لا يعترض البيع.**
- **`event_id` مشتقٌّ من الطلب (`purchase.{uuid}`)** لا مولَّدٌ عشوائيًّا: إعادة المحاولة بعد انقطاع الشبكة تحمل المعرّف نفسه فلا تُحتسب شراءً ثانيًا، ولو أُضيف حدث المتصفّح لاحقًا التقى به على المعرّف نفسه.
- **يُرسَل عند إنشاء الطلب لا عند تسليمه** — اتّساقًا مع أساس «الميزانية اليومية» (الطلبات المُدخَلة، والمرتجعات ≤ 5%). الانتظار أسبوعًا حتى التسليم كان سيحرم المنصّة من الإشارة التي تُحسِّن عليها أصلًا.
- **النسبة عبر `utm_content` لا عبر `fbclid`.** المنصّة لا تُخبرك بالحملة من معرّف النقرة — تعطيك معرّفًا يصلح للمطابقة لا للنسبة. فيحمل **رابط الإعلان نفسه** معرّفاته بمعاملاتٍ ديناميكية (`utm_content={{adset.id}}`)، ومنها نعرف الصنف والصفحة عبر `ad_external_maps` — الربط نفسه الذي يقوم عليه سحب الصرف، فلا مصدرَ ثانٍ للحقيقة. و`fbclid` يُحفَظ بصيغة `fb.1.{ms}.{id}` لأن Conversions API تحتاجه للمطابقة.
- **الحفظ في كعكة لا في الجلسة:** الزائر يصل من الإعلان اليوم ويشتري بعد يومين، وجلسة الضيف قد تُجدَّد بينهما فتضيع النسبة بصمت. و**آخر نقرةٍ تفوز** — نموذج المنصّة نفسه، ومخالفتُه تجعل أرقامنا تفترق عن أرقامها.
- **مساران للنسبة لا مسار واحد:** طلب الموظفة عبر حساب البزنس (كما كان)، وطلب الويب عبر معرّف المجموعة الإعلانية. و**كعكة الويب لا تُطبَّق على طلب موظفة**: موظفةٌ تصفّحت المتجر بعد نقر إعلان كانت ستُهدي طلباتها اليدوية لتلك الحملة.
- **ما لا يُربَط لا يُخمَّن:** مجموعة إعلانية غير مربوطة تُبقي الطلب بلا قناة ويُحفَظ معرّفها للربط لاحقًا. النسبة الخاطئة أسوأ من غيابها — غيابُها ظاهرٌ في التقرير وخطؤها ليس كذلك.
- **البكسل مستقلّ عن حسابَي القراءة والكتابة:** هو يخصّ **الموقع** لا الحساب الإعلاني ويُشارَك بينهما، فربطُه بأحدهما كان سيوقف القياس عند أول فصلٍ بينهما.
- **كل ما يُعرّف الزبون يُجزَّأ (SHA-256) قبل مغادرة الخادم**، والتطبيع قبل التجزئة شرطُ صحّتها: «0599…» و«970599…» يعطيان تجزئتين مختلفتين لشخصٍ واحد فتسقط المطابقة بلا شكوى. ولا تُرسَل حقول فارغة — المنصّة تعدّها إشارة مطابقةٍ رديئة.
- **حارس `runningInConsole()` أُسقط** بعد أن ألغى النسبة في الاختبارات كلّها: غياب الكعكة يكفي وحده، فالطلب المُنشأ في مهمّةٍ أو أمر سطرٍ لا كعكة له.
- **الاختبارات:** 12 اختبارًا على محرّك قياسٍ وهمي — لا نداء شبكي.
- **باقٍ خارج النطاق:** كتالوج المنتجات (feed) لربط معرّفات المحتوى بالصنف المُعلَن عنه، وأحداث `AddToCart`/`InitiateCheckout`، وفصل الحساب الإعلاني الثاني كيانًا في النظام (`ad_accounts`) ليعمل الطيّار عليه.

## ADR-053 — الطيّار الآلي للإعلانات (الكتابة إلى المنصّة) [**أُزيل في Phase 7.7** — بقرار المالك؛ الشيفرة في تاريخ Git]
- **السياق:** طلب المالك أن يدير النظام الإعلانَ يوميًّا وحده — يوقف الخاسر ويشغّل الرابح ويضبط الميزانية — مع سقفٍ يتحكّم فيه من اللوحة وملخّصٍ يومي. **العقل موجود أصلًا:** `AdBudgetService` يُخرج منذ Phase 7.2 حكمًا لكل (صنف × قناة) مبنيًّا على الربح الحقيقي بعد تكلفة الجملة والمرتجع. الناقص كان اليدَ والقفصَ والسجلّ.
- **الميزة على قواعد المنصّة الآلية:** قاعدة Meta تعرف «تحويلاتٍ» بتكلفةٍ ما، ولا تعرف تكلفة بضاعتك — فتُبقي صنفًا تكلفة طلبه أقلّ من عتبتها وربحُه أقلّ منها. هذا وحده يبرّر بناء الطبقة بدل استعمال الجاهز.
- **عقدٌ ثانٍ لا توسيعٌ للأول (`AdPlatformWriterInterface`):** رمز القراءة `ads_read` ورمز الكتابة `ads_management` منفصلان في `.env` (`META_ADS_WRITE_TOKEN`)، والمحرّك الافتراضي `null`. **غياب رمز الكتابة يُبقي المحرّك «غير مضبوط» ولو كان رمز القراءة حاضرًا** — فخطأٌ في مسار الاستيراد لا يملك أصلًا القدرة على إنفاق مال. ولو وُسّع العقد الأول لسقط الحاجز كلّه.
- **حدود العقد مقصودة:** يوقف ويشغّل ويعدّل ميزانية مجموعةٍ **قائمة**، ولا يُنشئ حملةً ولا إعلانًا ولا مادّةً إبداعية. الإنشاء يحتاج صفحةً ومادّةً ومراجعةً من المنصّة، وأخطاؤه لا تُلتقط بالتراجع كما تُلتقط أخطاء الإيقاف.
- **الفرملة تُؤتمت كاملة، والدوّاسة لا تُؤتمت:** إيقافٌ خاطئ يكلّف ربح يوم ويُتراجَع عنه بنقرة؛ وزيادةٌ خاطئة تصرف طوال الليل ولا تُستردّ. فالوضع `brake` ينفّذ `pause` و`decrease` وحدهما، و**`increase` غير مطبَّق في أي وضع** رغم أن الحكم يقولها — تُعرَض للإنسان ليقرّرها. عدم التماثل في المخاطر لا في الثقة.
- **مستويان قبل المال:** `suggest` (يكتب القرارات ولا يلمس المنصّة) ثم `brake`. الغاية أن يُقرأ سجلُّ الطيّار أسبوعين قبل منحه صلاحية التنفيذ: هل كان سيقرّر ما كنتَ ستقرّره؟
- **التهدئة والحدّ الأقصى للتخفيض ليسا تحفّظًا:** تعديل الميزانية بأكثر من ~20% يُعيد المجموعة إلى مرحلة التعلّم لدى المنصّة، فتعديلٌ يوميّ عنيف يُبقيها في التعلّم أبدًا — **أداءٌ أسوأ ممّا لو لم يتدخّل أحد**. الإيقاف وحده خارج التهدئة: لا تعلّم يُحفَظ في مجموعةٍ خاسرة.
- **السقف اليومي من اللوحة لا من `.env`** (المبدأ 8): هو الرقم الذي طلب المالك التحكّم فيه، وقيمةٌ في ملف البيئة تعني نشرًا على الخادم لكل تعديل — أي أن السقف الحقيقي سيبقى ما ضُبط أوّل مرّة. ويُطبَّق على **المجموع بعد الخطة**: ما تتركه الخطة يعمل، فإن تجاوزه أُوقفت الأقلّ ربحًا حتى ينزل تحته. وسقفٌ غير مضبوط (صفر) **لا يمنع الفرملة** — الإيقاف والتخفيض لا يزيدان الصرف أبدًا، وتعليقُهما على رقمٍ لا علاقة له بهما يترك خسارةً تجري بلا سبب.
- **الحالة تُقرأ حيّةً قبل كل قرار:** الميزانية قد تكون غُيّرت من لوحة المنصّة بعد آخر مزامنة، وتخفيضُ 20% من رقمٍ قديم يُنتج رقمًا لا يقصده أحد.
- **ميزانية على مستوى الحملة لا تُمَسّ:** `daily_budget = null` ليس صفرًا بل يعني CBO. تعديلها يطال مجموعاتٍ قد تكون رابحة، فيُسجَّل الامتناع ويبقى الإيقاف متاحًا — وهو كافٍ لغرض الفرملة.
- **`parent_external_id` على `ad_external_maps`:** الجدول كان يعرف «المجموعة ← صنف» و«الحملة ← صفحة» ولا يعرف أن تلك المجموعة داخل تلك الحملة، فكان الطيّار عاجزًا عن السؤال الوحيد الذي يحتاجه: أيّ مجموعةٍ أوقِف من أجل (صنفٍ على صفحة)؟ والقيمة موجودة في كل صفّ نتائج، فتُلتقط أثناء المزامنة بلا نداءٍ إضافي.
- **بلا إعادة محاولة على الكتابة:** نداءٌ نجح ثم انقطع الاتصال يُنفَّذ مرّتين إن أُعيد — وتكرار تخفيضٍ بنسبة يُنقص الميزانية مرّتين. يُبلَّغ الفشل ويُعاد القرار في دورة الغد بعد قراءة الحالة من جديد. وفشلُ مجموعةٍ واحدة لا يوقف الدورة.
- **الحفظ قبل الإرسال:** نداءٌ نجح ثم انقطع يترك المنصّة مُعدَّلة وسجلَّنا فارغًا — أسوأ الحالتين. الصفّ يُكتب أولًا فيبقى الأثر موجودًا ولو بحالة «فشل». وقرارٌ واحد لكل (يوم، مجموعة، مصدر) بفهرس فريد في القاعدة لا في الخدمة وحدها، فتشغيل الأمر يدويًّا أثناء عمل الجدولة لا يُخفّض مرّتين.
- **`ad_autopilot_decisions` شرطُ الأتمتة لا أثرُها الجانبي:** تُحفَظ **الأرقام التي بُني عليها القرار** لا القرار وحده — مراجعتُه بعد شهر تحتاج ما كان يراه يومئذٍ. و**يُسجَّل الامتناع كما يُسجَّل الفعل**: «لم أخفّض ولماذا» معلومةٌ يحتاجها صاحب العمل، وبغيرها يبدو الصمت رضًا. والتراجع يعيد ما كان **بالضبط** لا ما يُحسب من جديد.
- **الإيقاف الطارئ يطال كل مجموعة مربوطة** لا الصفحات المُسلَّمة للطيّار وحدها: من يضغط «أوقف كل الإعلانات» يقصد كلَّها. وهو فعلُ إنسانٍ صريح (`source = manual`) لا قرارُ خوارزمية.
- **المبالغ بالوحدة الصغرى وبعملة الحساب الإعلاني:** Meta تقبل الميزانية بالسنت، ومعاملُ التحويل يختلف بالعملة. خلطُ الوحدتين يصرف مئة ضعفٍ بلا أن ترفضه المنصّة، فالتحويل محصورٌ في دالّتين. ولا تحويل إلى الشيكل في هذه الطبقة: خطأٌ في سعر الصرف كان سيصير خطأً في المبلغ المصروف فعلًا.
- **الصلاحيات:** `marketing.autopilot.{view,manage}`. و«الإدارة» لمدير النظام وحده — هي **الصلاحية الوحيدة في النظام التي تُنفق مالًا خارجه**؛ حتى `manager` يرى ولا يضبط.
- **الاختبارات:** 19 اختبارًا على محرّك كتابةٍ وهمي. وما تحرسه ليس أن الطيّار يتصرّف بل أنه **لا يتصرّف حيث لا يجوز** — أكثر أخطاء الأتمتة كلفةً هي التي لا يشتكي منها أحد لأنها تصرف مالًا بهدوء.
- **خارج النطاق (بلا تنفيذ):** إنشاء الحملات والمواد الإبداعية، رفع الميزانيات آليًّا، اختيار الأصناف وإطلاق حملاتٍ لها. وهدف «الشراء عبر الموقع» يحتاج **Pixel + Conversions API** ونسبةَ الطلبات الإلكترونية (`fbclid`/UTM) — وكلاهما غير موجود، فلا تُبنى فوقه حملةُ مبيعاتٍ قبلهما.

## ADR-052 — سحب الصرف الإعلاني من المنصّة (قراءة فقط) [مُعتمد في Phase 7.3]
- **السياق:** الرقمان اللذان يُنسخان يدويًّا كل صباح (المُنفَق وعدد المحادثات) يأتيان من نداءٍ واحد على Marketing API. الأتمتة تُلغي العمل الروتيني وتُلغي معه سببَ حجب الأحكام: اليوم المنسيّ.
- **قراءة فقط، وبعقدٍ منفصل عن الكتابة.** `AdPlatformProviderInterface` يجلب ولا يُنشئ حملةً ولا يوقفها ولا يغيّر ميزانية. تشغيل الإعلانات من داخل النظام (مرحلة تالية بطلب المالك) يُضاف بعقد `AdPlatformWriterInterface` مستقلّ لا بتوسيع هذا — **الفصل هو الضمانة**: رمزُ القراءة (`ads_read`) لا يملك صلاحية الصرف، فخطأٌ في الاستيراد لا يمكن أن يُنفق مالًا. والصلاحيتان تُطلَبان من Meta على مستويين مختلفين، فلا تُمنح الأوسع مجانًا مع الأضيق.
- **المحرّك الافتراضي `null`:** النظام يعمل كاملًا بلا ربط، والإدخال اليدوي يبقى فوق المزامنة لا بديلًا مؤقّتًا عنها — الرمز يُبطَل، والشبكة تسقط، والمجموعة الجديدة تظلّ غير مربوطة. الأسرار في `.env` وحدها.
- **الربط بالمعرّف لا بالاسم (`ad_external_maps`):** المطابقة النصّية كل ليلة تنكسر عند أول إعادة تسمية أو اختلاف همزة، فيضيع صرفُ يومٍ **بصمت** ويبدو الصنف أربح ممّا هو. يُحفَظ الربط بالمعرّف مرّة واحدة، ويبقى الاسم للعرض. الحملة ⇄ قناة، والمجموعة الإعلانية ⇄ صنف.
- **الاقتراح لا يَربط:** المطابقة بالاسم (بتطبيع عربي: همزة، تاء مربوطة، ألف مقصورة، تشكيل) تُعرَض مرشَّحًا ويؤكّدها المستخدم — وزرُّ «اربط كل المقترحات» يجعلها نقرة واحدة. **ربط صنفٍ خطأً يَنسب صرفًا إلى صنفٍ لم يُعلَن عليه، وهو خطأ لا يظهر في أي رقم**: يبدو كلّ شيء سليمًا ويكون القرار مبنيًّا على وهم. وما لا يُربَط لا يُكتَب — لا يُخمَّن.
- **الجمع قبل الكتابة:** مجموعتان إعلانيتان تُعلنان الصنف نفسه على الصفحة نفسها تُجمعان في صفٍّ واحد؛ الكتابة المباشرة كانت ستُبقي آخر واحدة وتُسقط الأخرى فيبدو الصرف نصفَ ما هو.
- **إعادة سحب آخر 3 أيام لا أمسِ وحده:** أرقام Meta تُراجَع خلال 24–72 ساعة، فالرقم الأوّلي ليس نهائيًّا. بدونها يتجمّد صرفٌ ناقص ويُبنى عليه حكمُ إيقافٍ أو زيادة.
- **اليدويّ لا يُدهَس (`source`/`synced_*`):** قد يكون المستخدم صحّح رقمًا، ودهسُه يمحو تصحيحًا مقصودًا بلا أثر. تُسجَّل قيمة المنصّة بجانب اليدوية دائمًا، ويُعرَض الاختلاف في «الميزانية اليومية» ليقرّر المستخدم. وسعر صرف صفٍّ قائم لا يُعاد كتابته: ربح ذلك اليوم مُثبَّت عليه.
- **الاختبارات:** 15 اختبارًا كلّها على محرّك وهمي — **لا اتصال شبكي في أي اختبار**؛ اختبارٌ يعتمد على Meta الحقيقية رهانٌ على شبكةٍ وحسابٍ خارجيين لا اختبار.
- **المرحلة التالية (بلا تنفيذ):** الكتابة إلى المنصّة (إيقاف/زيادة/إنشاء) عبر `ads_management` — تحتاج مراجعة Meta وحرّاسًا إضافيّين (سقف يومي، تأكيد بشري، سجلّ قرارات)، لأن خطأً فيها يُنفق مالًا لا يُسترجَع.

## ADR-051 — الميزانية اليومية (الصرف الإعلاني اليدوي) [مُعتمد في Phase 7.2]
- **السياق:** المتجر يبيع عبر ثلاث صفحات فيسبوك بحملاتٍ منفصلة، والقرار اليومي «أوقف / أنقص / ثبّت / زد» يُتَّخذ بلا رقم. هذه المرحلة تبني **الأساس اليدوي** قبل نظام إدارة الحملات بالذكاء الاصطناعي — فالأتمتة تحتاج تاريخًا تُدرَّب عليه، ولا يُبنى التاريخ إلا بالقياس.
- **وحدة القرار (صنف × قناة) لا الصنف وحده:** الصنف قد يربح على صفحة ويخسر على أخرى (جمهور ومحتوى ومزايدة مختلفة)، وجمعُهما يُخفي الخسارة داخل متوسّط. وهي بنية مدير إعلانات Meta نفسها — الحملة = صفحة، والمجموعة الإعلانية = صنفٌ بميزانيته المستقلّة — فالصفّ عندنا يقابل صفًّا هناك ويُنسَخ منه رقمان.
- **الإسناد آليّ لا يدوي:** لكل صفحة **حساب بزنس مستقلّ** لدى شركة التوصيل، والموظفة مرتبطة بحسابها — فالسلسلة الطلب ← منشئُه ← حسابُ بزنسه ← الصفحة مكتملة بلا حقلٍ يملؤه الموظف. `ad_channels.delivery_business_id` **فريد**: حسابٌ واحد لصفحتين يَنسب مبيعات إحداهما للأخرى.
- **لقطة لا اشتقاق:** `orders.ad_channel_id` تُثبَّت في `Order::booted()` لحظة الإنشاء. الاشتقاق وقت العرض يقرأ الحاضر، فنقلُ موظفةٍ إلى صفحة أخرى كان سينقل معها **كل طلباتها السابقة** ويُغيّر تقرير الشهر الماضي بصمت. وُضعت في النموذج لا في `OrderService` لأن للطلب أكثر من مسار إنشاء.
- **`fx_rate` مخزَّن مع كل صفّ:** الصرف بالدولار والمبيعات بالشيكل، والإدخال يجري **في اليوم التالي** — فسعرُ يوم الإدخال كان سيحرّك ربح الأمس. ولذلك أيضًا التاريخ الافتراضي للصفحة **أمس** لا اليوم.
- **عدد المحادثات جزء من العقد لا زينة:** هدف الحملات «الرسائل»، فالنتيجة التي تقيسها Meta محادثةٌ لا طلب. تكلفة الطلب = تكلفة المحادثة ÷ نسبة التحويل، وهي ما يفصل **فشل الإعلان** (محادثات قليلة غالية) عن **فشل البيع** (محادثات رخيصة كثيرة بلا طلبات) — وإيقاف الإعلان في الحالة الثانية خطأ.
- **المصروف التشغيلي الثابت لا يُوزَّع على الأصناف (`operating_daily_costs`):** لا يتغيّر بإيقاف إعلانٍ أو زيادته، وتوزيعُه يجعل الصنف القليل الطلبات يبدو خاسرًا فيُوقَف إعلانٌ كان **يساهم** في تغطيته — بلا أن يوفّر إيقافُه منه شيئًا. صفوف الأصناف تقرّر الإعلان، وبطاقة اليوم تقرّر ربح النشاط. وبتاريخ سريان فلا يُعاد كتابة ربح الماضي.
- **الأساس على الطلبات المُدخَلة لا المسلَّمة** (قرار المالك: المرتجعات ≤ 5%): انتظار التسليم يؤخّر القرار أسبوعًا مقابل دقّةٍ لا تُذكر. والـ5% تُلتقط رغم ذلك — تُستبعَد حالة «مُرتجَع» وتُخصَم `returned_qty` بالتناسب، فيخرج المرتجع **حين يُسجَّل** بلا انتظار. **يفترق هذا عن أساس التقارير الثلاثة عمدًا** (تلك تُبقي المرتجع مبيعًا اتّساقًا مع ما اعتاده المستخدم)، والفارق محصورٌ في `AdBudgetService`.
- **الحكم:** نافذة 3 أيام؛ لا حكم دون 10 طلبات (الرقم القليل ضجيجٌ لا دلالة)، إلّا استثناءين فوريّين — **صرفٌ بلا محادثة**، و**صرفٌ يعادل ثلاثة أضعاف الهدف بلا طلب**. ويُحجب الحكم عند **ثغرة إدخالٍ داخل** النافذة (لا عند طرفيها، وإلّا بقيت كل حملة جديدة «بانتظار الإدخال»). العتبات وسعر الصرف والنافذة والحدّ الأدنى **كلّها من الإعدادات** (المبدأ 9)، ومصدرُ أرقامها ربحٌ ~72 ₪ على الطلب المُدخَل ⇒ تعادلٌ عند ~72، وعتبة الإيقاف عند 60 تترك هامش أمان.
- **الصلاحيات:** `reports.ad_budget.{view,manage}` — لمدير النظام والمدير وحدهما (الصفحة تكشف التكلفة والربح لكل صنف). في **migration وبذرة معًا**، فالنشر يشغّل `migrate` لا `seed`.
- **الحالة:** مُنفَّذ (27 اختبارًا). **خارج النطاق (بلا تنفيذ):** سحب الصرف من Meta API، Pixel وCAPI، الإيقاف/الزيادة التلقائيان، توليد المحتوى الإعلاني — كلّها تُبنى فوق هذا الأساس لاحقًا.

## ADR-050 — المحاسبة التشغيلية (Cashboxes · Banks · Vouchers · Expenses · Other Income · Transfers) [مُعتمد في Phase 7.1]
- **السياق:** طبقة محاسبة تشغيلية فوق محرّك القيد المزدوج القائم (ADR-029) دون إعادة بنائه: خزائن/بنوك، سندات قبض/صرف، مصروفات، إيرادات أخرى، تحويلات. **لا منطق أعمال في المتحكّمات؛ الخدمات/الأفعال فقط؛ معاملات ذرّية.**
- **إعادة الاستخدام الإلزامي:** كل ترحيل يمرّ حصريًا عبر `AccountingService::postEntry/reverse` (قيد متوازن، فحص الفترة المقفلة، تدقيق). **لا مساس مباشر بالأرصدة** — الرصيد يُشتقّ دائمًا من `accountBalance` على حساب GL المخصّص للخزينة.
- **الخزائن/البنوك (`treasuries`):** جدول موحّد بنوع `cash|bank`، كل خزينة مرتبطة **بحساب GL مخصّص فريد** (يُنشأ تلقائيًا تحت الأصول أو يُربط بموجود). الرصيد الافتتاحي يُرحَّل كقيد (مدين الخزينة / دائن حقوق الملكية) فيبقى الرصيد مشتقًّا. حذف آمن (يُمنع مع أي حركة/سند). الإيداع/السحب بين البنك والصندوق = تحويلات.
- **السندات الموحّدة (`financial_vouchers`):** نوع `receipt|payment|expense|income|transfer` بدورة حالة محروسة `draft → approved → posted (+ rejected/cancelled قبل الترحيل، reversed بعده)`. الترحيل **idempotent** (لا تكرار مع وجود `journal_entry_id`؛ مفتاح `idempotency_key`). **المُرحّل غير قابل للحذف — التصحيح بقيد عاكس** (`reversal_entry_id`). سطور القيد لكل نوع: قبض (مدين الخزينة/دائن المقابل)، صرف/مصروف (مدين المقابل/دائن الخزينة)، إيراد (مدين الخزينة/دائن الإيراد)، تحويل (مدين الوجهة/دائن المصدر). مرفقات (json)، أطراف اختيارية (عميل/مورد/موظّف)، ضريبة مُسجَّلة (تُدرَج بالمبلغ الإجمالي في هذه المرحلة).
- **الصلاحيات:** `accounting.{cashboxes,banks}.{view,manage}` و`accounting.{receipts,payments,expenses,income,transfers}.{view,create,approve,post}`. تُمنح للمدير/المحاسب.
- **التقارير واللوحة:** كشوف خزائن/بنوك برصيد جارٍ، تقرير سندات، حركة نقد يومية، ملخّص مصروفات/إيرادات شهري — كلّها **من القيود/السندات المُرحّلة** (لا إجماليات مكرّرة)؛ توسعة لوحة التحكّم بقسم مالي (أرصدة/قبض/صرف اليوم/غير مُرحّل/معكوس/مخطّط نقد).
- **الحالة:** مُنفَّذ (20 اختبارًا: ترحيل/عكس/idempotency/فترة مقفلة/صلاحيات/حذف آمن + HTTP). عربي RTL + إنجليزي + متجاوب + سندات قابلة للطباعة.
- **المراحل التالية (موثّقة، بلا تنفيذ):** ذمم العملاء، ذمم الموردين، كشوف العملاء/الموردين، تقارير الأعمار، قائمة الدخل، الميزانية العمومية، قائمة التدفّقات النقدية، التسوية البنكية، الإقفال السنوي.

## ADR-049 — وحدات الإدارة الإنتاجية (Users · Roles · Settings · Dashboard · AI Generator) [مُعتمد]
- **السياق:** استكمال وحدات الإدارة الأساسية قبل النشر: إدارة المستخدمين/الموظّفين، إدارة الأدوار والصلاحيات، إعدادات النظام الديناميكية، لوحة تحكّم تنفيذية، وزرّ «توليد بالذكاء الاصطناعي» لحزمة محتوى المنتج.
- **المستخدمون/الموظّفون:** CRUD كامل عبر `UserAdminService` (كلمة المرور مُجزَّأة، الأدوار عبر spatie، تدقيق تلقائي). حقول `department`/`job_title` (migration إضافي)، حالة نشط/معطّل، إعادة تعيين كلمة مرور مؤقّتة، بحث/فلاتر (اسم/بريد/دور/حالة). حمايات: لا حذف للذات ولا لآخر مدير. صلاحيات `settings.users.*`.
- **الأدوار والصلاحيات:** `RoleAdminService` — إنشاء/تعديل/نسخ/حذف آمن (يُمنع حذف `admin` أو دور مُسنَد لمستخدمين)، ربط الصلاحيات مجمّعة حسب الوحدة، بحث. RBAC فقط (المبدأ 11). صلاحيات `settings.roles.*`.
- **إعدادات النظام (ديناميكية من قاعدة البيانات):** عام/OpenAI/بريد/واتساب/توصيل/SEO/نظام عبر `SystemSettingsService` + `SettingsManager`. **الأسرار (مفاتيح API/كلمات المرور) تُخزَّن مُشفَّرة (Crypt) وتُقنَّع في الواجهة؛ .env له الأولوية وقت التشغيل** عبر جسر إعدادات في `FoundationServiceProvider` (يملأ config الفراغ فقط، محصَّن قبل توفّر الجدول). وضع صيانة عبر middleware يقرأ الإعداد (يمرّ المشرفون). صلاحيات `settings.system.*`.
- **لوحة التحكّم التنفيذية:** `DashboardController` **للقراءة فقط** فوق `ReportingService`/`WarehouseService` (مبيعات اليوم/الشهر، طلبات، إيراد، ربح، أعلى مبيعًا، نقص مخزون، أحدث الطلبات، ملخّص حالات التوصيل، أداء الموظفين، أداء التسويق، ملخّص المستودع، مخطّطات CSS). صلاحية `dashboard.view` (متاحة لكل الأدوار الموظّفة).
- **مولّد محتوى المنتج بالذكاء الاصطناعي (زر واحد):** توسعة العقد `generateBundle` (Null + OpenAI) — نداء واحد يُرجِع JSON بكل الحقول (وصف/مختصر/SEO/كلمات/وسوم/فئة مقترحة). المتحكّم يطابق الفئة/الوسوم المقترحة بالمعرّفات الموجودة (لا إنشاء تلقائي). **اقتراح فقط — يظهر في النموذج للتعديل ولا يُحفظ تلقائيًا.** يعيد استخدام الحدّ/التسجيل/التراجع من ADR-044.
- **رسوم التوصيل عند الإتمام (إكمال):** `CheckoutService` يطبّق رسوم توصيل من الإعدادات (`delivery.default_fee`/`delivery.free_threshold`) — افتراضي 0 (سلوك متطابق) مع شحن مجّاني فوق العتبة.
- **الحالة:** مُنفَّذ (24 اختبارًا جديدًا). عربي RTL + إنجليزي + متجاوب. **خارج النطاق (بلا تغيير):** الولاء/الكوبونات/Aliphia/تعدّد الفروع والمستودعات/مطالبات التوصيل.

## ADR-048 — جاهزية الإنتاج والأمان والأداء (Production Readiness) [مُعتمد في مرحلة الجاهزية]
- **السياق:** تحضير المنصّة للإنتاج (VPS، بلا نشر فعلي بعد): أمان، أداء، طوابير/جدولة، فهارس، كاش، Redis، وثائق نشر/نسخ احتياطي.
- **تتبّع التوصيات (إكمال ADR-045):** قسم التوصيات في المتجر يطلق **ظهورًا** (IntersectionObserver مرّة واحدة لكل قسم) و**نقرًا** (تفويض حدث) إلى `storefront.recommendations.track` عبر JS المتجر مع **إزالة تكرار** (مجموعة لكل حدث/منتج/موضع) واحترام جلسة الضيف/المُصادَق (كوكي + CSRF). يغذّي `recommendation_events` ولوحات KPI.
- **الأمان (Security Review):** حدّ معدّل على دخول/تسجيل/استرجاع كلمة مرور المتجر (throttle) وعلى نقطة التتبّع (60/د) وواجهة API (120/د) وwebhook التوصيل (60/د). رفع صور المرتجعات قُيّد إلى `mimes:jpeg,jpg,png,webp` (منع SVG المخزَّن/XSS). تحقّقات مؤكَّدة: CSRF افتراضي على كل الويب، لا حقن SQL (كل raw ثابت أو مُقيَّد ببارامترات)، لا mass-assignment (`$fillable` صريح في كل نموذج)، توقيع Opost عبر HMAC ثابت الزمن، أسرار في `.env` فقط (لا شيء متتبَّع)، سجلّات بلا أسرار.
- **الأداء:** فهارس إنتاجية إضافية للأعمدة الساخنة (تواريخ التقارير/الحالات) — migration واحد. إصلاح N+1 في بطاقة المتجر: `availableQty` صار مدركًا للتحميل المُسبق (`defaultVariant.inventoryStocks`) — سلوك متطابق مع رجوع للاستعلام. كاش لبيانات التنقّل (فئات/علامات) مع إبطال عند التعديل.
- **الطوابير:** الإرسال التسويقي الخارجي انتقل إلى `SendCampaignMessageJob` (ShouldQueue، `$tries=3`، backoff، آمن لإعادة المحاولة وidempotent عبر مفتاح الرسالة) — لا يحجب الطلب/الأمر. AI يبقى تزامنيًا (تفاعلي داخل واجهة المشرف، بمهلة/تراجع). webhook التوصيل تزامني لكنه idempotent (dedupe بـevent_id) وخفيف (تعيين حالة داخلي). مزامنة التوصيل مجدولة وidempotent (`withoutOverlapping`). Redis لـ cache/session/queue/rate-limit في الإنتاج.
- **الوثائق:** `.env.production.example` (بلا أسرار)، `deploy/supervisor/*`, `deploy/cron/*`, `docs/PRODUCTION_DEPLOYMENT.md` (Hostinger AlmaLinux 9 + cPanel)، `docs/OPERATIONS.md` (نسخ/استرجاع/فهارس/سجلّات append-only/الثوابت)، `docs/ACCEPTANCE.md` (خريطة تغطية سير العمل).
- **خارج النطاق (بلا تنفيذ):** الولاء/النقاط، الكوبونات الذكية، Aliphia، تعدّد الفروع/المستودعات، وحدة مطالبات التوصيل. النشر الفعلي للـVPS يبقى الخطوة التالية بعد المراجعة.

## ADR-047 — لوحات مؤشّرات الأداء الموسّعة (Expanded KPI Dashboards) [مُعتمد في Phase 6]
- **السياق:** لوحة مؤشّرات تنفيذية تجمع نمو المبيعات والتشغيل والتسويق في مكان واحد: إجمالي المبيعات، المُحصّل، غير المُسوّى، الربح الإجمالي، المبيعات حسب القناة/الموظّف، أرباح المسوّقين وعمولات الموظّفين، معدّل نجاح/استثناء التوصيل، معدّل المرتجعات، متوسّط قيمة الطلب، السلال المهجورة، الأعلى مبيعًا، أصناف نقص المخزون، أداء الحملات، نقرات/تحويلات التوصيات، واستخدام/تكلفة الذكاء الاصطناعي. نطاقات يوم/أسبوع/شهر/مخصّص.
- **القرار — توسعة `ReportingService` القائم (لا محرّك جديد):** تُضاف دالة واحدة `kpis(DateRange)` **للقراءة فقط** تجمّع فوق نفس جداول الأعمال (orders/order_items/delivery_settlements/commission_entries/shipments/return_requests/carts) وجداول Phase 6 الجديدة (`campaign_messages`/`recommendation_events`/`ai_generation_logs`). لا تكرار منطق ولا كتابة. الربح الإجمالي **تقريبي** (`Σ line_total − Σ qty×average_cost`) لعدم حفظ لقطة تكلفة بالسطر — موثّق صراحةً.
- **الصلاحيات:** `kpis.view` (مدير/مبيعات/محاسب). RTL عربي/إنجليزي + طباعة/PDF عبر مكوّنات `x-report` القائمة.
- **الحالة:** مُنفَّذ (3 اختبارات). لوحة واحدة تعيد استخدام مكوّنات التقارير (4.7).

## ADR-046 — أتمتة التسويق (Marketing Automation) [مُعتمد في Phase 6]
- **السياق:** محرّك حملات مستقلّ عن المزوّد يغطّي: سلة مهجورة، خمول، متابعة بعد التسليم، عيد ميلاد، إعلان منتج جديد، عاد للتوفّر، حالة الطلب، متابعة استثناء توصيل، تحديث مرتجع، استعادة العميل، توصيات. قنوات: واتساب/بريد/SMS/داخلي.
- **القرار — الإرسال حصريًا عبر `MessagingManager` (ADR-030):** `MessageDispatcher` هو النقطة الوحيدة للإرسال، ويطبّق حوكمة قبل أي إرسال: **موافقة (opt-in من `communication_preferences`)**، حجب (`message_suppressions` = opt-out)، ساعات هدوء، حدّ تكرار، و**idempotency** (مفتاح ثابت للثلاثي حملة/عميل/مرجع). لا مزوّد يُستدعى من متحكّم/نموذج، ولا أسرار في المستودع.
- **دورة الحياة:** `Campaign` (uuid + soft-delete + auditable) بحالات محروسة `draft → pending_approval → approved → active → paused → completed → archived`. التحفيز بحدث عبر `MarketingEventSubscriber` (يجسر أحداث الدومين القائمة: OrderDelivered/ReturnRequested/ReturnCompleted/DeliveryStatusChanged) → `CampaignService::handleTrigger`. المجدولة عبر أوامر (`marketing:run-birthdays` يوميًا، `marketing:run-abandoned-carts` كل ساعة). `AudienceResolver` يبني الجمهور من فلاتر معتمدة (عيد ميلاد/خمول/فئة/وسم) بلا بيانات جديدة.
- **الجداول:** `campaign_templates`, `campaigns`, `campaign_messages` (سجلّ تنفيذ: حالة/محاولات/`idempotency_key` فريد/`is_test`), `message_suppressions`. القوالب والنصوص عربي/إنجليزي مع متغيّرات `{{name}}`.
- **الاختبارات لا ترسل حقيقةً:** `FakeMessagingProvider` (driver `fake` في `config/messaging`) يسجّل الإرسال في الذاكرة فقط. 9 اختبارات تغطّي الموافقة/الحجب/الهدوء/التكرار/idempotency/الانتقالات/الإرسال التجريبي.
- **الحالة:** مُنفَّذ. الصلاحيات `marketing.campaigns.{view,manage,approve}`, `marketing.templates.manage`, `marketing.reports.view`.

## ADR-045 — محرّك التوصيات (Product Recommendations) [مُعتمد في Phase 6]
- **السياق:** توصيات على صفحات المنتج/السلة/الإتمام: ذات صلة، مشابهة، يُشترى معًا، عملاء اشتروا أيضًا، بيع تكميلي/ترقية، ملحقات مكمّلة، الأعلى مبيعًا، شخصية.
- **القرار — تنفيذ عقد المتجر القائم (`StorefrontRecommendationProvider`, ADR-034):** `RuleBasedRecommendationProvider` يحلّ محلّ `Null` عبر `config/storefront.php` **دون تعديل المتجر** (تبديل عبر الإعداد؛ رجوع لـNull بـ`STOREFRONT_RECOMMENDATION_PROVIDER=null`). المنطق في `RecommendationService` **من الكتالوج وتاريخ الطلبات فقط** (موثوق أولًا)، مع نقطة امتداد لمزوّد ذكاء اصطناعي مستقبلًا (ينفّذ العقد نفسه).
- **التوافر إلزامي:** لا يُوصى أبدًا بمنتج غير مفعّل/محذوف/غير ظاهر/**نافد** — أساس `availableBase` يشترط رصيدًا متاحًا (`Σ on_hand − reserved > 0`) في المستودع الرئيس الوحيد.
- **تحكّم يدوي:** `product_recommendations` (include = تثبيت، exclude = حجب) لكل (منتج/نوع) يُدمج فوق النتيجة الحسابية. يُسجَّل **المصدر والسبب** على كل منتج (سمات عابرة) لتتبّع الأداء.
- **التتبّع:** `recommendation_events` (ظهور/نقر/تحويل) عبر نقطة متجر عامّة `storefront.recommendations.track` — تغذّي لوحات KPI (ADR-047).
- **الحالة:** مُنفَّذ (4 اختبارات). الصلاحيات `recommendations.{view,manage}`. RTL أوّلًا. **بلا تخصيص/تنميط عميق للعميل** خارج البيانات المعتمدة.

## ADR-044 — مساعد محتوى المنتجات بالذكاء الاصطناعي (AI Product Content) [مُعتمد في Phase 6]
- **السياق:** مساعد داخل صفحة إنشاء/تعديل المنتج يقترح: عنوان عربي/إنجليزي، وصف مختصر/تفصيلي، مزايا، مواصفات، عنوان/وصف/كلمات SEO، منشور تواصل، نص واتساب. يدعم إعادة توليد/اختصار/توسيع/نبرة/لغة.
- **القرار — طبقة تكامل خلف عقد (المبدأ 13):** `AiContentProviderInterface` + مزوّدون (`NullAiContentProvider` افتراضي/بديل آمن بلا شبكة، `OpenAiContentProvider`). الربط من `config/ai.php`. **لا يُستدعى مزوّد من متحكّم/نموذج** — `AiContentService` (المزوّد محقون) هو المنسّق. إضافة مزوّد = صنف + إدخال إعداد.
- **اقتراح دائمًا — لا نشر تلقائي:** الخدمة **لا تكتب أي حقل منتج**؛ تُرجِع نصًّا يراجعه الموظّف ويطبّقه يدويًا (لوحة `x-admin.ai-panel` عبر AJAX، زرّ «تطبيق» ينقل النص للحقل). **لا اختراع مواصفات** غير مُعطاة (نظام المُوجّه + قالب Null يعيد صياغة المدخلات فقط).
- **الأمان:** الأسرار في `.env` فقط (`config/services.php:openai`) — لا مفاتيح في الكود/المستودع. `ai_generation_logs` **append-only** يسجّل المستخدم/المنتج/النوع/المزوّد/الطراز/الرموز/الحالة **بلا أسرار**. حدّ معدّل لكل مستخدم (`RateLimiter`)، معالجة مهلة/إعادة محاولة/**تراجع رشيق** إلى القالب الآمن. صورة المنتج تُرسَل فقط عند تفعيل التحليل البصري + طلب صريح.
- **الحالة:** مُنفَّذ (6 اختبارات). الصلاحيات `ai.content.use`, `ai.config.manage`, `ai.logs.view`.

## ADR-043 — تعزيزات المستودع والمخزون (Warehouse & Inventory) [مُعتمد في Phase 5]
- **السياق:** استكمال إدارة المستودع فوق محرّك المخزون القائم (2.4) دون إعادة تصميم: **جرد فعلي (stock-take)، تنبيهات نقص، بحث باركود، عمليات دفعية، ولوحة مستودع**. الأرصدة/الحركات/الدفتر/الحجز/الخصم عند الشحن/الإرجاع التلقائي كلّها **قائمة وتُعاد استخدامها كما هي**.
- **مبدأ إلزامي — كل تغيير مخزون عبر `InventoryService`:** أي تسوية (جرد/دفعة) تمرّ حصريًا عبر `adjustIn/adjustOut`، فتُسجَّل `inventory_movements` + `inventory_ledger` + التدقيق تلقائيًا. **لا مساس مباشر بالأرصدة ولا تكرار منطق.**
- **الجرد الفعلي (جديد):** `inventory_counts` (uuid/رقم CNT/حالة counting→review→completed+cancelled/نطاق) + `inventory_count_items` (لقطة `system_qty` مقابل `counted_qty` والفرق). `InventoryCountService`: فتح (لقطة أرصدة النظام)، تسجيل (بالصنف أو الباركود أو دفعة)، مراجعة، **إكمال يطبّق الفرق مقابل الرصيد الحالي عبر المحرّك** (يضمن أن يصبح on_hand = المعدود).
- **تنبيهات النقص (تعزيز):** يعاد استخدام `inventory_stocks.reorder_level`/`reorder_qty` **القائمة** (لا عمود جديد)؛ استعلام `on_hand ≤ reorder_level` + تقرير/لوحة + صلاحية `inventory.alerts.view`.
- **الباركود:** بحث دقيق `product_variants.barcode` ثم `products.barcode` (المتغيّر الافتراضي) — نقطة `WarehouseService::findByBarcode` + مسار API/شاشة مسح للجرد.
- **الدفعات:** `InventoryBatchService::adjust` يطبّق فروقًا موقّعة متعدّدة ذرّيًا عبر المحرّك.
- **مستودع واحد رئيسي:** WH-MAIN القائم (`is_default`)؛ لا تغيير على النموذج. الصلاحيات الجديدة `inventory.counts.{view,manage}`, `inventory.alerts.view`, `inventory.batch` (تُضاف لدور warehouse/manager/admin عبر `InventoryPermissionSeeder`).
- **الحالة:** مُنفَّذ (جرد/تنبيهات/باركود/دفعات/لوحة، 12 اختبارًا). عربي/إنجليزي RTL متجاوب. لا إعادة تصميم لأي وحدة مكتملة.

## ADR-042 — التقارير والتحليلات التشغيلية (Operational Reports) [مُعتمد في Phase 4.7]
- **السياق:** لوحات وتقارير تشغيلية تنفيذية/مبيعات/طلبات/توصيل/مالية + أداء موظفين/مسوّقين/منتجات + إحصاءات عملاء/شركات توصيل/مرتجعات. بنطاقات يومي/أسبوعي/شهري/مخصّص، تصدير Excel/PDF، بحث/فلترة، رسوم، RTL عربي/إنجليزي، متجاوبة للجوّال.
- **القرار — طبقة قراءة فقط، لا تكرار منطق:** وحدة `app/Modules/Reporting` (`ReportingService`) **تجميعات SQL فوق نفس جداول الأعمال القائمة** (orders/order_items/commission_entries/shipments/delivery_status_transitions/return_requests/delivery_settlements/payments/customers). **لا تكتب شيئًا ولا تعيد حساب أي منطق** — تقرأ الدفاتر والجداول التي تكتبها خدمات المراحل 4.1–4.6 (العمولة من `commission_entries`، المال من `delivery_settlements`/`payments`، إلخ). أداء عبر group-by مفهرسة.
- **النطاق الزمني:** `DateRange` (day/week/month/custom) — فلترة `whereBetween` على `created_at`/`delivered_at`/`posted_at` حسب التقرير.
- **التصدير:** **Excel = CSV بترميز UTF-8 مع BOM** (تنزيل حقيقي، يفتحه Excel بالعربية). **PDF = طباعة المتصفّح** (`window.print()` + CSS طباعة يخفي التنقّل) — يضمن تشكيل العربية RTL بلا اعتماديات ولا مخاطر خطوط. لا تُضاف حزم PDF ثقيلة.
- **الرسوم:** أشرطة CSS/نِسَب مُقدَّمة من الخادم (بلا مكتبة JS) — متجاوبة وRTL وقابلة للطباعة.
- **الصلاحيات:** مسارات القراءة محكومة بـ`can:reports.view` (مدير/مشرف مبيعات/محاسب/مالية/عمليات توصيل). لا كتابة، لا حالة.
- **الحالة:** مُنفَّذ (5 لوحات + 6 تقارير + تصدير + بحث + رسوم، 10 اختبارات). **بذلك تكتمل المرحلة 4** (عدا 4.5 المُستبعَدة).

## ADR-041 — التسوية المالية ومطابقة المزوّد (Financial Settlement) [مُعتمد في Phase 4.6]
- **السياق:** مطابقة بيان تسوية مزوّد التوصيل (COD محصّل، رسوم، خصومات، صافٍ) بسجلّاتنا، وترحيلها محاسبيًا. **إضافي بالكامل**؛ يُعيد استخدام المحاسبة والعمولات دون تكرار. (المرحلة 4.5 مطالبات التوصيل **مُستبعَدة** — الخصومات ذات الطابع المطالبي تُعالَج كبنود خصم عامّة في السطور.)
- **الجداول:** `delivery_settlements` (مزوّد/فترة/حالة + إجماليات **مُبلَّغة** من البيان و**محسوبة** من سجلّاتنا + `variance` + `accounting_entry_id`)؛ `settlement_lines` (لكل طلب/شحنة: COD + رسوم + خصم + صافٍ + `reported_cod`/`matched`/`variance`). حالات `draft → reconciled → posted → closed` (+ cancelled) محروسة. soft-delete + auditable.
- **الأساس المحسوب:** COD = `orders.total` للطلب المرتبط بشحنة **مُغلقة** (`delivery_status=closed`)؛ الرسوم = مجموع `shipment_fee_components`. `net = cod − fees − deductions`.
- **المطابقة وكشف التباين:** `reconcile` يحسب الإجماليات، يطابق `reported_cod` لكل سطر (matched/variance)، ويحسب تباين الصافي إجماليًا. لا يمنع الترحيل مع تباين موثّق.
- **الترحيل المحاسبي (إعادة استخدام `AccountingService::postEntry`، ADR-029):** قيد مزدوج متوازن — **Dr نقد (`1010`) بالصافي + Dr مصروف الشحن (`5020`) بالرسوم + Dr الخصومات (`5030`) = Cr ذمم شركات التوصيل (`1050` — حساب COD clearing مُضاف)**. مرتبط بالتسوية عبر `reference_type/id`. لا محاسبة يدوية مكرّرة.
- **تأكيد الاستحقاق (idempotent):** عند الترحيل تُعلَّم الطلبات `settled_at` وتُستدعى `accrueForOrder`+`markEligibleForOrder` — **مؤكِّدة لما جرى عند إغلاق التوصيل (4.3)** لا مُكرِّرة (الاستحقاق يمسّ pending فقط، وsettled_at يُضبَط مرّة). الملكية للدور `finance` (صلاحيات `settlements.{view,manage,reconcile,post}`).
- **العلاقة مع الإغلاق (4.3):** إغلاق التوصيل يُفعّل الاستحقاق تشغيليًا؛ التسوية المالية **تطبّق الأثر المحاسبي وتطابق المال مع المزوّد** — الطبقتان idempotent ومتكاملتان.

## ADR-040 — المرتجعات والاستبدال RMA (Returns & Exchanges) [مُعتمد في Phase 4.4]
- **السياق:** تفعيل تدفّق ADR-011/BR-RET-* فعليًا: طلب مرتجع/استبدال/إبدال مرتبط بطلب مُسلَّم، بسير موافقات ووجهة مخزون/مالية عكسية. **إضافي بالكامل**؛ يُعيد استخدام الخدمات القائمة دون تكرار.
- **إعادة الاستخدام (المبدأ 12، لا تكرار منطق):** المخزون عبر `InventoryService` (طريقتان مُضافتان `returnToStock`=`return_in`→on_hand و`returnToDamaged`=`damage_out`→damaged — تستخدمان محرّك الحركات القائم؛ كل حركة مسجَّلة في الحركات/الدفتر)؛ الاسترداد عبر `PaymentService::refund`؛ عكس العمولة عبر `CommissionService::reverseForOrder` (كامل) / `adjustForReturn` (جزئي تناسبي، BR-RET-09)؛ حالة الطلب عبر `OrderService::markReturned/markPartiallyReturned/markExchanged` (مُضافة — تُفعّل مفاتيح `returned/partially_returned/exchanged` القانونية)؛ الشحنة المرتبطة عبر `ShipmentService::createLinkedShipment`.
- **التدفّق القانوني (المتطلّب):** `return_request → approved → received → inspected → completed` (+ `rejected`/`cancelled`) بانتقالات محروسة. مسار الموافقة **مبيعات → مشرف مبيعات → مستودع → قرار نهائي** ممثَّل بالمراحل والصلاحيات.
- **الأنواع/الأسباب:** أنواع `return`/`exchange`/`replacement`؛ أسباب مُصنّفة (`wrong_item`, `damaged`, `missing_item`, `customer_refused`, `delivery_company_issue`, `internal_warehouse_mistake`, `changed_mind`, `other`)؛ تسويات `refund`/`no_refund`/`store_credit`/`replacement`. مدعوم: إرجاع كامل/جزئي، استرداد/بلا استرداد، استبدال كامل/جزئي، إبدال فقط.
- **الفحص وتوجيه المخزون (BR-RET-04):** لكل بند نتيجة (`sellable/damaged/wrong_item/missing_parts/quarantine`) وتوجيه (`restock`→on_hand، `damaged`→دلو التالف، `none`). تتبّع `order_items.returned_qty` يمنع تجاوز الإرجاع ويميّز الكامل عن الجزئي.
- **شحنة مرتبطة لا تعديل للأصل (المتطلّب):** إن استلزمت شركة التوصيل شحنة مختلفة للمرتجع/الاستبدال، تُنشأ `shipments` جديدة بـ`kind` (`return_pickup`/`exchange_delivery`) و`parent_shipment_id` — **الأصل يبقى دون مسّ** (تجاوز حارس «شحنة واحدة لكل طلب» عبر `createLinkedShipment` المخصّصة).
- **لا حذف — بل عكس (BR-RET-11)، والذرّية (BR-RET-12):** كل خطوة ذات أثر داخل معاملة؛ الأثر عبر حركات جديدة. الصور اختيارية (`return_request_photos`)، الخطّ الزمني/سجلّ الحالة والتدقيق كاملان (`return_request_events` + Auditable).
- **الصلاحيات/الأدوار:** `returns.{view,create,approve,receive,inspect,finalize,refund}` (ADR-021) موزّعة على sales/sales_supervisor/warehouse/finance/manager. واجهات API + لوحة RTL موبايل-أوّلًا.
- **مؤجّل (موثّق):** دفتر الرصيد الدائن الفعلي (`store_credit`/credit_note — BR-RET-08)، وإعادة احتساب عمولة البيع الجديد للبديل (تُستحقّ عند تسليم/إغلاق شحنة الاستبدال).

## ADR-039 — بنية عمليات التوصيل (استثناءات · Webhook · مزامنة · رسوم · خطّ زمني) [مُعتمد في Phase 4.3]
- **السياق:** إكمال Phase 4.3 فوق محرّك الحالات (ADR-038) بالبنية التشغيلية للمزوّد. كلّها **عبر طبقة تجريد المزوّد** (`DeliveryProviderManager` + `DeliveryProviderInterface`) — لا منطق مزوّد في وحدات الأعمال، ودعم عدّة مزوّدين دون تغيير المنطق.
- **مُحلّل متعدّد المزوّدين:** `DeliveryProviderManager::driver(code)`/`forShipment()` يحلّ الـDriver من `config/shipping.php` بحسب كود مزوّد الشحنة/المسار — استيعاب/مزامنة/webhook كلّها تحلّ المزوّد الصحيح ديناميكيًا.
- **محرّك الاستثناءات:** `delivery_exception_categories` (قابلة للضبط: SLA/تصعيد/دور لكل فئة) + `delivery_exceptions` (حالة `open→in_progress→escalated→resolved→reopened`، مسؤول، مهلة SLA، عدّاد إعادة فتح) + `delivery_exception_notes` (append-only). `DeliveryExceptionService`: فتح/إسناد/ملاحظة/تصعيد/حلّ/إعادة فتح + **تصعيد مجدول** (`escalateOverdue` عبر `delivery:escalate-exceptions`).
- **بنية Webhook:** نقطة عامّة `POST /api/v1/webhooks/delivery/{provider}` — **تحقّق توقيع في الـDriver** (`verifyWebhookSignature`، HMAC لـOpost؛ فشل التوقيع ⇒ 401 `unverified`)، **idempotency + حماية من التكرار** (تجاهل event_id مُعالَج + قيد `delivery_provider_transitions` الفريد)، وتسجيل كامل في `delivery_provider_events`. كل استيعاب حالة يمرّ عبر `DeliveryStatusService::applyProviderStatus` (لا تكرار).
- **المزامنة المجدولة:** `DeliverySyncService::syncActive` (أمر `delivery:sync`، مفعّل بالإعداد) يستطلع **الشحنات النشطة فقط** (غير النهائية، لها مزوّد، دون تجاوز `max_attempts`)، **يكشف تعارضات المزوّد** (حالة قانونية غير قابلة للانتقال ⇒ `inconsistent`)، **يعيد محاولة الفاشلة** (`sync_attempts`/`sync_error`)، وسجلّ تدقيق في `delivery_provider_events` (channel=sync). idempotent (يتجاهل الحالة غير المتغيّرة).
- **محرّك الرسوم (مستقلّ عن المزوّد):** `shipment_fee_components` (type/amount/owner/source) — أنواع قابلة للتوسّع من `config/delivery.php` (delivery/cod/oversize/overweight/remote_area/return/exchange/retry/manual/discount). `DeliveryFeeService`: إضافة/لقطة عرض/إجمالي/تفصيل حسب المالك. **لا ربط بمنطق مزوّد.**
- **الخطّ الزمني الموحّد:** `ShipmentTimelineService` يدمج (للقراءة) الحالة الداخلية + حالة المزوّد + أسباب التعليق + إجراءات المستخدم + أحداث webhook + أحداث المزامنة زمنيًا (بلا تخزين).
- **الصلاحيات:** إضافة `shipping.delivery.fees`؛ إدارة الاستثناءات تحت `shipping.delivery.manage`؛ الـwebhook عامّ (توقيع).
- **الحالة:** مُنفَّذ (30 اختبارًا إجماليًا لـ4.3). Phase 4.3 مكتملة.

## ADR-038 — محرّك حالة التوصيل القانوني (Canonical Delivery Status Engine · تعيين Opost) [مُعتمد في Phase 4.3]
- **السياق:** سير عمل التوصيل الرسمي (مصدره Opost، 10 حالات) يجب أن يصبح **دورة الحياة القانونية** للتوصيل داخل النظام، ويحكم الاكتمال المالي واستحقاق العمولات. أسماء Opost مضلّلة (`cod_pickup` = سُلّم للعميل والنقد لدى المندوب، `delivered` = بضاعة مرتجعة عائدة إلينا) فلا تُستخدم كمفاتيح قانونية.
- **القرار — حالة داخلية قانونية منفصلة عن المزوّد:** عمودان على `shipments`: `delivery_status` (قانوني، تقرأه وحدات الأعمال) و`provider_status` (خام، للعرض/التتبّع فقط). المفردات القانونية في `App\Modules\Shipping\Support\DeliveryStatus` (ثوابت + رسم انتقالات + أسباب تعليق) — ثابتة بالكود (تحكم منطقًا ماليًا)، لا في جدول قابل للإدارة.
- **التعيين في الـDriver (المبدأ 13):** `DeliveryProviderInterface::mapProviderStatus()` يعيّن حالة المزوّد الخام ← قانوني. **كل منطق Opost محصور في `OpostDeliveryProvider`** (خريطة `STATUS_MAP`)؛ إضافة/تبديل مزوّد = Driver جديد + إعداد، دون لمس منطق الأعمال. Null Driver يُرجِع null.
- **السجلّات (append-only، منفصلة):** `delivery_status_transitions` (سجلّ قانوني: from/to/actor_type[user/system/provider]/actor/reason_code/note/provider_status/وقت) و`delivery_provider_transitions` (سجلّ مزوّد خام + `payload` + مفتاح idempotency فريد `(provider, event_id)` للـwebhook). لا تعديل ولا حذف.
- **أسباب التعليق المُصنّفة (قابلة للتقرير):** قائمة معتمدة تُلزَم عند `on_hold` اليدوي؛ لقطة `on_hold_reason` على الشحنة + تقرير تجميعي.
- **احتساب العمولة عند `in_accounting` (FUNDS_AT_ACCOUNTING) — ADR-012d:** عند وصول المبلغ لمحاسبة المندوب (Opost: `in_accounting`) يجري عبر `DeliveryStatusService` ضمن معاملة: `accrueForOrder`+`markEligibleForOrder` (pending → **eligible**) لموظف المبيعات والمسوّق — **شرط أن تكون قيمة البضاعة المحصّلة من العميل بدون التوصيل (`total − shipping_total`) أكثر من 1**. مسار الإرجاع (`return → delivered → close`) لا يمرّ بهذه الحالة إطلاقًا ⇒ **لا عمولة على المرتجعات**. `delivered_cod_held` لا يجعلها مستحقّة (تبقى pending). **لا دفع تلقائي**.
- **الفاتورة تصبح «مدفوعة» عند `in_accounting` والتحصيل يدخل «صندوق الأونلاين» (ADR-012g):** وصول المبلغ لمحاسبة المندوب هو إثبات أن **العميل دفع**، فيقع ضمن معاملة الانتقال وبنفس شرط قيمة البضاعة > 1: (1) `OrderPaymentService::markCollected` — `amount_paid = total` و`payment_status = paid` (idempotent)؛ (2) **فقط عند انتقال فعلي غير مدفوع → مدفوع**: `collectCodToTreasury` يُنشئ **سند قبض مُرحّلًا** — مدين خزينة **«صندوق الأونلاين»** / دائن **«ذمم شركة التوصيل 1050»** بكامل الإجمالي — فتُقفَل ذمّة الطلب على 1050 ويظهر المبلغ رصيدًا في الصندوق. اشتراط الانتقال الفعلي يستثني تلقائيًا الطلبات المدفوعة إلكترونيًا مسبقًا (المندوب لم يقبض) ويمنع الازدواج عند تكرار الحدث. الخزينة: إعداد `delivery.cod_treasury_id` (شاشة الإعدادات ← التوصيل)، وإلا `CB-ONLINE` («صندوق الأونلاين»، GL `1011-0002` — أُنشئ بmigration `2026_08_11_210000` + TreasurySeeder)، وإلا أي خزينة اسمها يحوي «اونلاين». مسار الإرجاع لا يمرّ بالحالة ⇒ لا تُعلَّم المرتجعات مدفوعة ولا سند لها. **تسوية التوصيل** (SettlementService) صار طرفها الدائن **صندوق الأونلاين** (fallback: 1050 إن لم تُهيَّأ خزينة) — فتُفرغه عند توريد المزوّد: مدين النقد الرئيسي + أجور التوصيل / دائن الصندوق.
- **حذف المستند المُرحّل يعكس قيده ولا يحذفه (ADR-016b — قرار المالك، قبل التشغيل الفعلي):** حذف **طلب البيع** (`OrderVoidService`) و**فاتورة المشتريات** (`PurchaseInvoiceService::deletePosted`) صار يُنشئ **قيدًا عاكسًا** بدل حذف القيد الأصلي. الأثر المالي مطابق للحذف تمامًا (صفر — الأرصدة والتقارير تُحسب من القيود المُرحّلة فيلغي العاكس الأصل)، والمكسب: **لا فجوات في ترقيم القيود** (كانت `deleteEntry` تُبقي أرقامًا مفقودة يلفت غيابها أي مدقّق) وسبب تغيّر الأرصدة يبقى مقروءًا. القيد **غير المُرحّل** (مسودّة) يُحذف كما كان لأن أثره المالي معدوم، والمعكوس سابقًا يُتخطّى (idempotent). المستند نفسه يبقى **محذوفًا ناعمًا** فلا يزعج شاشات العمل. بهذا توحّد السلوك: كل حركة مُرحّلة (سند أو قيد مستند) تُعكس ولا تُمحى. **يبقى استثناءً مقصودًا:** `SalesPostingService::repost/unpost` يُحدّث سطور القيد في مكانه أو يحذف قيد تكلفة أصبح صفرًا — تصحيح بيانات قبل خروج المال، لا حركة نقدية.
- **رسوم التوصيل خارج الدفاتر (ADR-012h — قرار المالك):** المندوب يقبض رسوم التوصيل من العميل ويحتفظ بها أجرةً له، فهي **مرور عابر** لا تخصّنا: لا تُقيَّد إيرادًا (أُلغي سطر «إيراد الشحن 4020» من قيد البيع) ولا مصروفًا ولا ذمّة. المصدر الوحيد للمبلغ القابل للقيد هو `SalesPostingService::bookableTotal()` = `total − shipping_total`، ويُستعمل في **قيد البيع** و**سند تحصيل COD** و**سطور تسوية التوصيل** معًا — فتبقى الذمّة على «ذمم شركة التوصيل 1050» مطابقة تمامًا لما يُورَّد إلينا وتُقفَل بالكامل (لو حُصّل الإجمالي لصار الحساب دائنًا بقيمة التوصيل). **يبقى `orders.total` شاملًا التوصيل** لأنه فاتورة العميل ومبلغ COD المُرسَل للمزوّد، وكذلك `amount_paid` عند التسديد — الفصل محاسبي فقط. أثر جانبي مقصود: إن اختلفت أجرة شركة التوصيل عمّا يُحصَّل من العميل، لا يظهر الفرق في الأرباح.
- **لا تسديد يدويًا لطلبات التوصيل (قرار المالك):** أُلغي زر «تحويل إلى مدفوعة» ومساره وصلاحيته (كان تجاوزًا للأدمن). **حالة شركة التوصيل هي المصدر الوحيد** لتسديد فاتورة التوصيل: `in_accounting` ⇒ مدفوعة + سند التحصيل. يمنع هذا تضارب مصدرَي حقيقة، ويحمي من إخراج شحنة بمبلغ تحصيل صفر (الـDispatcher يشتقّ «الدفع عند الاستلام» من `payment_status`). المبيعات المباشرة (pos) تبقى على زر «دفع» بسند قبض وخزينة — مديونيتها على العميل لا على شركة التوصيل. إن تعطّلت المزامنة يبقى العلاج تشغيليًا: إعادة المزامنة، لا التسديد اليدوي.
- **CLOSE = الإغلاق المالي النهائي للشحنة (المتطلّب 4):** عبر `DeliveryStatusService` ضمن معاملة: `orders.settled_at` (مُضاف) + حدث `ShipmentClosed` (نقطة امتداد للترحيل المحاسبي 4.6). **لا يُعاد احتساب العمولة هنا** (تمّ عند `in_accounting`) — يمنع منح عمولة للطرود الراجعة التي تصل `close` عبر مسار الإرجاع.
- **دفع الأرباح بمبلغ حرّ موثّق محاسبيًا (ADR-012e، مُعدَّل):** الدفع يقع **مقابل رصيد المستفيد** لا مقابل بنود محدّدة. `CommissionService::payAmount` يُنشئ **سند صرف مالي** (`kind=payment`) **ويعتمده ويُرحّله فورًا** (قرار المالك — كان مسودّة تنتظر المالية): يخرج المبلغ من الخزينة/البنك المختار ويُقيَّد مصروف العمولات لحظة الضغط، وتُسجَّل الدفعة `status=paid` مع `paid_at`. حساب المصروف يُحسم تلقائيًا من `accounting.commissions.expense_account` (5040) ما لم يُمرَّر صراحةً. الرصيد مشتقّ: `المستحق − المدفوع (سند مُرحّل) − قيد الاعتماد (سند مسودّة/معتمد إن وُجد من قبل)`؛ المبلغ قد يقلّ/يزيد عن المستحق (سلفة = رصيد سالب). **التصحيح بعكس السند لا بحذفه** (ADR-016).
- **الترحيل المحاسبي للمرتجعات (ADR-012f):** إتمام المرتجع يُنشئ عبر `ReturnPostingService` ضمن معاملة قيدين: (1) **عكس الإيراد** — مدين «مردودات المبيعات 4030» (حساب مقابل للإيراد، رصيده مدين فيُخصم تلقائيًا من الإيراد) / دائن **نفس حساب مديونية الطلب** المستخدم عند البيع، بالقيمة **الصافية** المباعة (بعد الخصم) للكميات المرتجعة؛ (2) **عكس التكلفة للبضاعة الصالحة فقط** (`inventory_route=restock`) — مدين المخزون / دائن تكلفة البضاعة المباعة بلقطة تكلفة وقت البيع. البضاعة **التالفة** (`damaged`) أو **غير العائدة** (`none`) تبقى تكلفتها مصروفًا في COGS لأنها خسارة فعلية بلا قيمة مخزون. idempotent عبر `return_requests.revenue_entry_id`. **لا يمسّ النقد:** الاسترداد النقدي الفعلي سند منفصل — فإن كان العميل قد سدّد يصبح رصيد مديونيته دائنًا (مبلغ مستحقّ الردّ) حتى يُصرف.
- **استيعاب «قفزات» المزوّد (ADR-039a):** المزامنة تستطلع كل عدّة دقائق بينما الطرد قد يتنقّل بين عدّة حالات في ثوانٍ (وقد يضيع حدث webhook)، فتصل حالة أبعد من المسموح بخطوة واحدة. سابقًا كان الانتقال يُرفض وتعلق الشحنة على حالتها القديمة للأبد (تُعلَّم `inconsistent`). الآن `DeliveryStatus::path()` يحسب **أقصر مسار قانوني**، ويُسار خطوة خطوة مع تسجيل كل انتقال (`note` يوضّح أنها خطوة وسيطة مستنتجة) وتثبيت حالة المزوّد الخام على الخطوة الأخيرة فقط. **الأمان أوّلًا:** يُقبل المسار **الوحيد** فقط؛ عند تعدّد المسارات بنفس الطول (مثلًا `picked_up → closed` عبر مسار التحصيل أو مسار الإرجاع) يُترك للمراجعة البشرية لأن الاختيار الخاطئ يمنح/يمنع عمولة بغير حق.
- **تصحيح تعيين حالات الإرجاع لدى Opost:** `return`/`returned` = الطرد راجع وموجود في المكتب ⇒ `returning_to_courier` (كان `returned` يُعيَّن خطأً إلى `return_in_transit` فيقفز مرحلة ويصبح الانتقال غير قانوني). `delivered` = الطرد الراجع دخل فاتورة إرجاع في طريقه إلينا ⇒ `return_in_transit`.
- **تفعيل المزامنة إلزامي:** `DELIVERY_SYNC_ENABLED` افتراضيها `false` ولم تكن موثّقة في `.env.example`، فكانت حالات الطرود لا تتحدّث إطلاقًا رغم سلامة التكامل. أُضيفت للقالب مع `DELIVERY_SYNC_CRON` و`OPOST_WEBHOOK_SECRET`.
- **التحديث الفوري لحالات التوصيل (ADR-039b):** ثلاث طبقات متكاملة — (1) **webhook** على `POST /api/v1/webhooks/delivery/opost` = تحديث لحظي؛ التوقيع **اختياري** (يُفرض فقط عند ضبط `OPOST_WEBHOOK_SECRET`) فيعمل فورًا حتى لو لم يوقّع المزوّد، مع idempotency عبر `event_id` ومطابقة الشحنة بـ`external_id` أو `tracking_number`. (2) **مزامنة مجدولة كل دقيقة** (`DELIVERY_SYNC_CRON` افتراضها `* * * * *`) كشبكة أمان إن ضاع حدث. (3) **زر «مزامنة الآن»** في صفحة الشحنة لاستطلاع لحظي عند الطلب (يصفّر `sync_attempts` كي لا تُستبعد شحنة فشلت سابقًا) مع عرض آخر مزامنة وحالة المزوّد الخام ووسم «تحتاج مراجعة يدوية».
- **تصحيح التقاط أحدث حالة من `status_history`:** كان الاختيار بالمعرّف الرقمي الأكبر فقط، فتُلتقط **أقدم** حالة حين تكون المعرّفات نصّية (UUID) وتُطبَّق حالة قديمة. صار الترتيب: الطابع الزمني ← المعرّف الرقمي ← ترتيب المصفوفة.
- **تغطية كل حالات Opost الاثنتي عشرة:** كانت `pending_pickup` و`on_deliver` **غير معيَّنتين إطلاقًا**، والحالة غير المعروفة تُتجاهَل بصمت فلا تتغيّر الحالة عندنا. أُضيفتا (`pending_pickup` ⇒ `ready_for_pickup`، `on_deliver` ⇒ `picked_up`) مع مرادفات بالمسافة (`"on deliver"`) وتحصين لخطأ «Darfts» الإملائي في واجهتهم. اختبار يحرس التغطية الكاملة لكل تبويب.
- **إظهار سبب فشل الإرسال (ADR-039c):** كان سبب فشل إرسال الطلب لشركة التوصيل يُكتب في سجلّ الأخطاء فقط، فيظهر الطلب «بانتظار التتبّع» بلا تفسير حتى تنجح محاولة المكنسة لاحقًا (تأخير غامض). صار يُخزَّن على الطلب (`delivery_dispatch_error/attempts/attempted_at`) ويُعرض في قائمة الطلبات، ويُمسح تلقائيًا عند النجاح.
- **شاشة أحداث المزوّد:** `admin/shipping/provider-events` تعرض كل حدث وارد (webhook/مزامنة) بنتيجته وحمولته الخام وسبب الرفض، مع ملخّص 24 ساعة وحالة وصول الـwebhook ورابطه — للإجابة فورًا: هل يصلنا شيء؟ ولماذا لم تُطبَّق الحالة؟
- **الاستيعاب idempotent:** أحداث المزوّد قد تصل خارج الترتيب؛ الانتقال القانوني غير المسموح يُوثَّق كحالة مزوّد فقط دون تغيير القانوني ولا رمي استثناء (الانتقالات اليدوية صارمة تُرفَض).
- **الصلاحيات/الأدوار:** `shipping.delivery.{view,manage,sync,close}` (ADR-021)؛ دور `delivery_ops` (view/manage/sync)؛ `close` مقصور على `finance`/`manager`.
- **الحالة:** مُنفَّذ محرّك الحالات الأساسي + تعيين Opost + السجلّات + التقارير + الأثر المالي عند الإغلاق (15 اختبارًا). استثناءات SLA/التصعيد وربط الـwebhook الحيّ ورسوم التوصيل تبقى ضمن بقية 4.3.

## ADR-037 — عمليات المرحلة 4 (Operations: Assisted Sales · Affiliate · Delivery · Returns · Claims · Settlements) [مُعتمد؛ التنفيذ بالدفعات]
- **السياق:** المرحلة 4 تعكس سير العمل التشغيلي الفعلي لتوفير أونلاين (12 مجالًا). ضخمة جدًا؛ تُقسَّم إلى دفعات مستقلة قابلة للاختبار/الاعتماد كما المرحلة 3. المرجع الكامل: [`PHASE_4_OPERATIONS_DESIGN.md`](PHASE_4_OPERATIONS_DESIGN.md).
- **المبادئ المُلزِمة:** إعادة استخدام Orders/CRM/Inventory/Shipping/Payments/Accounting/Permissions/Events وطبقات المزوّدين **دون إعادة تصميم** (تغييرات إضافية فقط)؛ متحكمات رفيعة والمنطق في خدمات؛ **دفاتر غير قابلة للتعديل** (لا حذف — عكس، ADR-011/016)؛ قيود قاعدة بيانات؛ تدقيق؛ مسارات موافقة؛ Webhook **idempotent**؛ RTL + إنجليزي. **يُمنع** أي منطق نمو/ولاء/سلة ذكية/توصيات/Meta Ads/أتمتة تسويق (ADR-032).
- **الدفعات:** 4.1 البيع المُساعد + الأدوار + تعديل السعر بالموافقة واللقطات؛ 4.2 دفاتر العمولة/الأرباح (حالات pending→eligible→approved→paid + adjusted/reversed)؛ 4.3 عمليات التوصيل وتكامل المزوّد + الاستثناءات؛ 4.4 RMA + الفحص وتوجيه المخزون؛ 4.5 مطالبات التوصيل؛ 4.6 التسويات والمطابقة (تُفعّل الاستحقاق + قيود محاسبية)؛ 4.7 التقارير. **الاستحقاق لا يُفعَّل إلا بعد التسوية الناجحة** (المتطلّب 11) — الدفاتر تبقى pending/earned حتى 4.6.
- **الأدوار:** تُضاف `sales_supervisor` (4.1)، `delivery_ops` (4.3)، `warehouse_manager` (4.4)، `finance` (4.6) — إضافةً للقائمة.
- **قرارات 4.1 (مُنفَّذة):** توسعة مفردات `orders.channel` النصّية بـ`whatsapp/instagram/messenger/phone/other` (لا هجرة نوع)؛ `orders.affiliate_id` (FK users، nullable)؛ لقطات على `order_items` (`retail_price_snapshot`, `wholesale_cost_snapshot`, `price_change_reason`, `price_approved_by`)؛ **دفتر `order_price_changes` غير قابل للتعديل**؛ `AssistedOrderService` يُعيد استخدام `OrderService::create`/`CustomerService` (لا تكرار منطق). قاعدة الموافقة: `new_price < min_price` أو `< wholesale_cost` يتطلب اعتماد مشرف ما لم يملك المنفّذ `sales.orders.override_price` (BR-EMP-05/BR-PRICE-06). صلاحيات `sales.orders.{assist,override_price}`.
- **بلا تناقض مانع:** كيان المسوّق/المحفظة مؤجّل لـ4.2 (4.1 يكتفي بالإسناد)؛ الأسئلة المفتوحة (نافذة الإرجاع/أثر الاستبدال على العمولة/الرصيد السالب) تخصّ 4.2/4.4 وتُحسم عند اعتمادها.
- **قرارات 4.2 (مُنفَّذة):** محرّك `CommissionService` يستحقّ تلقائيًا عند حدث `OrderDelivered` (مستمع `AccrueCommissionsOnDelivery`)؛ العمولة الافتراضية **1%** قابلة للضبط بجدول `commission_rules` (نطاقات: موظف/فترة/حملة/منتج/فئة/فرع/دور)؛ أرباح المسوّق = هامش `(سعر البيع − لقطة تكلفة الجملة) × الكمية`. **دفاتر append-only غير قابلة للتعديل**: `commission_entries` (حركات موقّعة accrual/adjustment/reversal، حارس نموذجي يمنع تعديل الحقول المالية) + `commission_transitions` (سجل انتقالات) + `commission_payouts`/`commission_payout_entries`؛ **الرصيد مُشتقّ لا مخزّن**. دورة الحياة `pending→eligible→approved→paid` (+`adjusted/reversed/cancelled`) بانتقالات مُتحقَّقة؛ **الأهلية تُمنح فقط بالتسوية (4.6)** عبر `markEligibleForOrder` — ليست بالإنشاء/التسليم (المتطلّب 11). أسبقية حتمية (موظف>حملة>منتج/فئة>فرع>دور>عام)؛ منع اعتماد/دفع مزدوج (قيد فريد `uniq_entry_paid_once` + `lockForUpdate`)؛ صرف جزئي لكل مستفيد. جاهزية المرتجعات عبر `adjustForReturn`/`reverseForOrder` (حركات جديدة دون مسّ التاريخ)؛ جاهزية محاسبية بلا قيود نهائية قبل التسوية. صلاحيات `commissions.{view_own,view_team,rules.manage,approve,payout,audit.view}`؛ أدوار `finance`/`sales_supervisor`.
- **الحالة:** التصميم كامل مُعتمد؛ **4.1 و4.2 مُنفَّذتان**؛ 4.3–4.7 تُنفَّذ بالتتابع بعد اعتماد كل دفعة.

## ADR-036 — المصادقة والهوية (Authentication & Identity) [مُعتمد في Phase 3.5]
- **السياق:** الدفعة 3.5 تُكمل طبقة المصادقة والهوية فوق حساب 3.4 دون إعادة تصميم: تسجيل/دخول قياسي (بريد أو **هاتف**/كلمة مرور)، **استرجاع كلمة مرور**، تذكّرني، خروج آمن، **دخول اجتماعي (Google/Facebook)**، ربط هويّات، دمج الضيف، وإدارة الحساب. **يُمنع تنفيذ** الولاء/مكافآت الميلاد/السلة الذكية/التوصيات/الكوبونات/أتمتة التسويق/Meta Ads/Facebook Pixel/التحليلات — نقاط امتداد فقط.
- **الدخول الاجتماعي (طبقة تكامل — المبدأ 13):** عقد `SocialAuthProvider` + تنفيذ `SocialiteAuthProvider` (Laravel Socialite) + DTO `SocialUserData` محايد؛ يُبدَّل بمزوّد وهمي في الاختبارات (دون OAuth حقيقي). المزوّدون من `config/social.php`؛ **الأسرار في `.env` حصريًا** عبر `config/services.php` (المبدأ 5). أمان: تحقّق الحالة/الـcallback داخل Socialite، CSRF قياسي، ونيّة (login/link) في الجلسة.
- **الهوية والربط (منع التكرار):** جدول `social_identities` (معرّفات المزوّد منفصلة؛ `(provider, provider_id)` فريد؛ لا أسرار). `SocialAuthService`: هوية قائمة → دخول؛ **بريد موثّق قائم → ربط آمن** (البريد الاجتماعي موثّق من المزوّد)؛ وإلا حساب جديد. **لا حساب مكرّر أبدًا.** ربط/فكّ ربط من إدارة الحساب مع حماية «آخر وسيلة دخول».
- **إكمال الملف قبل الشراء:** مستخدمو الدخول الاجتماعي ناقصو البيانات (هاتف/ميلاد/لغة/تفضيلات تواصل) يُوجَّهون لشاشة إكمال عبر `EnsureProfileComplete` على مسار `/checkout`. `Customer::isProfileComplete()` يشتقّ الاكتمال (لا عمود حالة).
- **دمج الضيف (موسَّع):** `GuestMergeService` يوحّد عند الدخول/التسجيل: دمج السلة (3.4)، **ربط طلبات الضيف المؤهّلة** (قاعدة CRM — تطابق الهاتف المطبّع)، مع الحفاظ على العناوين/الإشعارات (مملوكة أصلًا)؛ مفضّلة الضيف غير قائمة (نقطة امتداد).
- **مخطط إضافي فقط (لا إعادة تصميم):** `social_identities`؛ `users.terms_accepted_at`؛ **`customers.primary_phone` صار nullable** (عملاء الدخول الاجتماعي بلا هاتف حتى الإكمال) — تغيير موسّع لا كاسر.
- **إعادة استخدام الخدمات (لا تكرار منطق):** التسجيل الاجتماعي يُنشئ العميل عبر `CustomerService`؛ الدمج عبر `CartService`/`GuestMergeService`؛ استرجاع كلمة المرور عبر وسيط Laravel القياسي (روابط تشير لواجهة المتجر عبر `ResetPassword::createUrlUsing`). متحكمات رفيعة.
- **الشروط والخصوصية:** خانة قبول مطلوبة عند التسجيل العادي (`terms` accepted) → `terms_accepted_at`؛ قبول ضمني عند «المتابعة عبر…».
- **الواجهة:** أزرار Google/Facebook بعلامات رسمية على الدخول والتسجيل، RTL + إنجليزي، mobile-first، مُوسومة (aria)؛ صفحات المصادقة `noindex`.
- **الفصل عن محرّك النمو:** لا أي منطق نمو/تحليلات/بكسل؛ حقول الهوية جاهزة للربط لاحقًا فقط (ADR-032).
- **الاختبارات:** 12 اختبار هوية (تسجيل Google/Facebook + هوية + إكمال؛ ربط بريد قائم دون تكرار؛ منع التكرار؛ دمج سلة الضيف؛ حارس الشراء؛ ربط/فكّ ربط + حماية آخر وسيلة؛ استرجاع كلمة مرور؛ دخول بالهاتف؛ إلزام الشروط؛ ربط طلب ضيف بالهاتف) → **349 ناجحة**؛ Pint نظيف؛ بناء الإنتاج ناجح.

## ADR-035 — تجربة حساب العميل (Customer Experience Layer) [مُعتمد في Phase 3.4]
- **السياق:** الدفعة 3.4 تبني **طبقة تجربة العميل الكاملة** فوق الوحدات القائمة دون إعادة تصميمها ودون تكرار منطق أعمال. تشمل: التسجيل/الدخول، دمج سلة الضيف عند الدخول، الملف، العناوين المحفوظة (تعدّد + افتراضي)، **تاريخ ميلاد مطلوب عند التسجيل** (جاهزية مكافآت الميلاد/التسويق)، «طلباتي» + التتبّع + إعادة الطلب، المفضّلة (Wishlist)، مركز الإشعارات، التفضيلات (لغة/فرع/قنوات تواصل)، والإعدادات. **يُمنع الآن تنفيذ الولاء/مكافآت الميلاد/السلة الذكية/الكوبونات/التوصيات/العروض/التسويق** — فقط تهيئة الحساب لتتّصل بها مستقبلًا دون إعادة تصميم مخطط.
- **المصادقة (جلسة الويب):** حساب المتجر عبر حارس `web` (منفصل عن مصادقة الإدارة/Sanctum). التسجيل يُنشئ `User` بدور `customer` + سجلّ `Customer` مرتبط (عبر `CustomerService` — تطبيع الهاتف/الأبناء) + إشعار ترحيبي معامَلاتي. صفحات الحساب محميّة بـ`require.customer` (توجيه غير المُصادَق إلى دخول المتجر)، وكلّها **noindex**.
- **دمج سلة الضيف (المتطلّب):** عند الدخول/التسجيل يُقرأ رمز سلة الضيف من كوكي `cart_token` (يكتبها `storefront.js`)، وتُدمج بنودها في سلة المستخدم عبر `CartService::mergeGuestIntoUser` (تراكم + تعليم سلة الضيف `merged`). لا تغيير على واجهة السلة (3.1/3.2).
- **مخطط إضافي فقط (ADR-032 — لا إعادة تصميم):** أعمدة على `customers` (`birth_date`, `preferred_locale`, `preferred_branch_id`, `communication_preferences` JSON, `acquisition_source`) — جاهزية تسويق تُخزَّن فقط؛ جدول `wishlist_items` (فريد لكل عميل/منتج)؛ جدول إشعارات Laravel القياسي (`notifications`) كصندوق داخل التطبيق.
- **إعادة استخدام الخدمات (لا تكرار منطق):** `AccountService` (تنسيق التسجيل/الدمج/إعادة الطلب) يُعيد استخدام `CustomerService`/`CartService`؛ عناوين وتفضيلات العميل عبر **دوال مُضافة إلى `CustomerService`** (نفس قاعدة «افتراضي واحد» — BR-CUST-06)؛ «طلباتي» عبر `Customer::orders()`؛ إعادة الطلب عبر `CartService::addItem` (تُتجاوز البنود غير المتاحة)؛ `WishlistService` بسيط.
- **التتبّع «الحيّ»:** صفحة تتبّع تعرض المسار الزمني (`order_status_history`) + حالة الدفع/الشحن، مع استطلاع دوري خفيف (JSON `orders/{order}/status`) لتحديث الحالة. الملكية مفحوصة (403 لطلب/عنوان الغير).
- **مركز الإشعارات (جاهزية القنوات):** قناة `database` كصندوق داخل التطبيق الآن؛ القنوات الخارجية (WhatsApp/Email/Push) تُضاف مستقبلًا كقنوات إشعار مخصّصة تُوجَّه عبر **طبقة المراسلة القائمة** (`MessagingManager` — ADR-030) دون إعادة تصميم. لا مزوّد خارجي الآن.
- **RTL/موبايل/SEO/تحليلات:** كل الصفحات RTL أساسي + إنجليزي، mobile-first (تخطيط شريط جانبي متجاوب)، صفحات الحساب `noindex` (خاصّة)، وأحداث تحليلات عبر مُرسِل الأحداث القائم (نقاط امتداد — بلا مزوّد). نقاط امتداد النمو (ADR-032) تبقى محفوظة: حقول الميلاد/التفضيلات/القنوات والمفضّلة **جاهزة للربط** بالولاء/الحملات/الذكاء لاحقًا.
- **API/المسارات:** `/account/{login,register,logout}` + `/account` (لوحة) + `profile`/`password` + `orders`/`orders/{order}`/`status`/`reorder` + `addresses` (CRUD + default) + `wishlist`/`toggle` + `preferences` + `notifications`.
- **مؤجّل بخُطّافات موثّقة (بلا تنفيذ):** الولاء/النقاط، مكافآت الميلاد، الكوبونات/العروض، التوصيات/السلة الذكية، أتمتة التسويق، تتبّع حيّ بالبثّ (WebSockets)، أسماء ثنائية اللغة للفئات/العلامات.
- **الاختبارات:** 11 اختبار تجربة (توجيه الضيف، التسجيل ينشئ مستخدمًا/عميلًا بتاريخ ميلاد ودور وإشعار، إلزام تاريخ الميلاد، دمج سلة الضيف، دخول/خروج، «طلباتي» مُنطاقة + تتبّع + منع طلب الغير، إعادة الطلب تملأ السلة، CRUD العناوين + افتراضي واحد، تبديل المفضّلة، حفظ التفضيلات، مركز الإشعارات) → **337 ناجحة**؛ Pint نظيف؛ بناء الإنتاج ناجح.

## ADR-034 — واجهة المتجر (Storefront Catalog) [مُعتمد في Phase 3.3]
- **السياق:** الدفعة 3.3 تبني **واجهة المتجر العامّة** المواجِهة للعميل (تصفّح/اكتشاف/سلة/تنقّل للإتمام) فوق الوحدات القائمة دون إعادة تصميمها ودون تكرار منطق أعمال في المتحكّمات/القوالب.
- **العرض (SSR للـSEO):** صفحات مُخدَّمة من الخادم بـBlade + Tailwind + Alpine، **عربي RTL أساسي + إنجليزي**، mobile-first. القراءة عبر `StorefrontService` (طبقة قراءة فقط) التي تُعيد استخدام: نطاقات `Product::active()/visible()`، وكيانات Category/Brand، و**تسعير/توافر من `CartService`** (`sellingPrice`/`availableQty` — لا تكرار منطق). توافر مدرك للفرع عبر `availableQty(Product, ?Branch)` (يحصر بمستودعات الفرع).
- **الهوية واللغة:** `store.identity` (من 3.2) يخدم السلة للمستخدم/الضيف؛ `storefront.locale` (Middleware) يضبط اللغة من الجلسة (مبدّل `/lang/{locale}`). لا تعديل لوحدات مكتملة.
- **السلة/الإتمام (إعادة استخدام API):** تُنفَّذ من العميل (Alpine) عبر واجهات 3.1/3.2 بهوية مزدوجة — الضيف برمز سلة (`X-Cart-Token` في localStorage)، والمُصادَق بـBearer إن وُجد. لا منطق أعمال في الواجهة.
- **SEO:** روابط slug نظيفة (`/p/{slug}` · `/c/{slug}` · `/b/{slug}`)، meta title/description (من حقول المنتج مع بدائل)، Open Graph/Twitter، canonical، و**بيانات مهيكلة JSON-LD** (Product على التفاصيل، ItemList على القوائم).
- **جاهزية التسويق/التحويل (ADR-032 — بلا منطق نمو):** عقد `StorefrontRecommendationProvider` + `NullRecommendationProvider` (يخدم «مميّز» من `is_featured` و«وصل حديثًا» من الأحدث — حقائق كتالوجية — ويُعيد best-sellers/related/FBT/cross-sell/upsell/bundles/personalized **فارغة**). أقسام العرض تُخفى تلقائيًا حين تكون فارغة → نقاط امتداد جاهزة. شارة العرض من `promo_price` (كتالوج)؛ عتبة الشحن المجاني من `config/storefront.php` (null = بلا رسالة). التبديل لمحرّك النمو عبر الإعداد دون تعديل المتجر.
- **جاهزية التحليلات (بلا مزوّد):** `storefront.js` يُطلق أحداث نافذة (`storefront:analytics`) لـ`ProductViewed`/`CategoryViewed`/`SearchPerformed`/`ProductAddedToCart`/`ProductRemovedFromCart`/`CheckoutStarted` — نقاط اشتراك لمزوّد مستقبلي.
- **UX/الوصولية:** بطاقات سريعة (lazy images، line-clamp)، سعر/توفّر واضحان، معرض صور، حالات فارغة/تحميل/خطأ، نماذج وتنقّل مُوسومة (labels/aria)، RTL وخط Tajawal.
- **المسارات (web):** `/` (رئيسية) · `/shop` · `/search` · `/categories` · `/brands` · `/c/{slug}` · `/b/{slug}` · `/p/{slug}` · `/cart` · `/checkout` · `/lang/{locale}`. المنتج/الفئة/العلامة تُحلّ بالـslug مع نطاق الإتاحة (404 للمخفي/غير الفعّال).
- **مؤجّل بخُطّافات موثّقة:** محرّك التوصيات/العروض الفعلي، best-sellers، صفحة تسجيل دخول للمتجر ودمج سلة الضيف عند الدخول (من 3.2)، مزوّد تحليلات خارجي، أسماء ثنائية اللغة للفئات/العلامات (المخطط الحالي عربي فقط لها).
- **الاختبارات:** 14 اختبار واجهة (رئيسية، قائمة تعرض المعروض فقط، تفاصيل بـSEO/JSON-LD/إضافة للسلة، 404 للمخفي، فلترة فئة/علامة، بحث، فلترة/ترتيب سعر، ترقيم، حالة فارغة، فهارس الفئات/العلامات، تبديل اللغة والاتجاه، إضافة للسلة ضيفًا ومُصادَقًا) → **326 ناجحة**؛ Pint نظيف؛ بناء الإنتاج (Vite) ناجح.

## ADR-033 — إتمام الشراء متعدّد الخطوات (Multi-Step Checkout) [مُعتمد في Phase 3.2؛ مُنقَّح بقرار المالك]
- **السياق:** الدفعة 3.2 تحوّل السلة النشطة (3.1) إلى **طلب مبيعات** عبر الخدمات القائمة دون منطق أعمال جديد. **قرار المالك المُعتمد (تنقيح):** دعم **المستخدم المُصادَق والضيف**، واستبدال النقطة الذرّية الواحدة بـ**جلسة إتمام متعدّدة الخطوات**، مع **الحفاظ على معاملة الإنشاء الذرّية النهائية وبدء الدفع كما نُفّذا**، بأدنى تغييرات إضافية ودون إعادة تصميم الوحدات المكتملة.
- **الهوية المزدوجة (إضافي):** طبقة `store.identity` (Middleware) تقبل مستخدمًا مُصادَقًا (Sanctum) أو ضيفًا برمز سلة `X-Cart-Token` (UUID)، وترفض بـ401 عند غياب الهوية (يحافظ على سلوك 3.1). سلة الضيف عبر `carts.session_token` القائم (لا تغيير مخطط) بفرع افتراضي. `CartService::resolveActive/forGuest` مضافان (سلوك `forUser` سلوك 3.1 بلا تغيير).
- **جدول إضافي واحد `checkout_sessions`:** (uuid، `cart_id`، `user_id` اختياري، `session_token` للضيف، status pending/placed/abandoned، لقطة الشحن + `payment_method_code` تتراكم عبر الخطوات، `order_id` عند الإتمام). لا تعديل لـ`orders`/`payments`/المخزون.
- **الخطوات (`CheckoutService`، تنسيقي بحت):** `start(cart)` يرفض السلة الفارغة ويُنشئ/يُعيد جلسة معلّقة ويُطلق `CheckoutStarted` → `update(session, data)` يضبط لقطة الشحن/الدفع تدريجيًا → `place(session)` يتحقّق من الاكتمال وإعادة التوافر (`assertPurchasable`) ثم يستدعي **المعاملة الذرّية المحفوظة** `placeOrder`: `OrderService::create` (لقطة عميل من الجلسة + بنود السلة، `channel=web`) → `confirm` → `reserveStock` (**يحجز المخزون — معيار قبول المرحلة 3**) → `PaymentService::initiate` (COD يبقى pending — ADR-028) → تعليم السلة `converted`، ثم `CheckoutCompleted` بعد نجاح المعاملة.
- **العميل واللقطة:** لقطة العميل تُشتقّ من الجلسة؛ `customer_id` من السلة (مستخدم مرتبط) أو null (ضيف)؛ منع العميل المحظور عبر `OrderService` (BR-CUST-12). اللقطة ثابتة (ADR-030).
- **الأحداث المستقرّة (ADR-032):** `CheckoutStarted` (عند البدء؛ `user` صار اختياريًا للضيف) و`CheckoutCompleted` (بعد نجاح الإتمام). لا مستمع الآن — نقاط امتداد لسياق النمو.
- **الوصول والملكية:** الجلسة تخصّ نفس الهوية (تطابق `user_id`، أو تطابق `session_token` للضيف) — تُفحص في المتحكّم (403 عند عدم التطابق). `UpdateCheckoutSessionRequest` يتحقّق من الحقول إن حضرت (`payment_method_code` عبر `exists` + فحص `is_active` عند الإتمام).
- **API:** `POST /store/checkout` (بدء) · `GET /store/checkout/{session}` · `PUT/PATCH /store/checkout/{session}` (تحديث) · `POST /store/checkout/{session}/place` (إتمام).
- **نقاط امتداد مؤجّلة موثّقة (ADR-032، بلا تنفيذ):** الكوبونات/العروض/محرّك التسعير، استرداد الولاء/المكافآت، طلبات الهدايا ورسائلها، Save For Later/Buy Again/Express/One-Click، اختيار عنوان محفوظ عبر API، تسعير الشحن الفعلي (`shipping_total=0` حتى مرحلته)، دمج سلة الضيف مع الحساب عند تسجيل الدخول.
- **الاختبارات:** 13 اختبار إتمام (هوية الضيف/المصادقة، رفض السلة الفارغة، تدفّق متعدّد الخطوات كامل، انعكاس الحجز، تحويل السلة، رفض الإتمام الناقص، رفض طريقة دفع غير مُفعّلة عند الإتمام/غير معروفة عند التحديث، رفض نقص المخزون، الأحداث، منع الوصول لجلسة الغير، **إتمام ضيف كامل**، منع الضيف برمز غير مطابق) + سلة 3.1 (9) دون تغيير → **312 ناجحة**.

## ADR-032 — سياق النمو وذكاء التجارة (Growth & Commerce Intelligence) — جاهزية معمارية فقط [مُعتمد كتوجيه معماري، بلا تنفيذ]
- **السياق:** تطوّر المنصّة من متجر إلكتروني إلى **منصّة تجارة حديثة**. المستقبل يتطلّب وحدات تسويق ونمو متقدّمة (سلة ذكية، توصيات، عروض، ولاء/مكافآت/كاش-باك، كوبونات، إحالات، أتمتة تسويق، حملات، تقسيم عملاء، تحليلات، تتبّع تحويل). **هذا القرار توجيه معماري للجاهزية فقط — لا يُنفَّذ أي من هذه الميزات الآن ولا يُوقف خارطة الطريق ولا يُعاد تصميم أي وحدة مكتملة.** المرجع الكامل: [`GROWTH_COMMERCE_ARCHITECTURE.md`](GROWTH_COMMERCE_ARCHITECTURE.md).
- **السياق المحدود (Bounded Context):** يُعرَّف سياق مستقبلي باسم **«Growth & Commerce Intelligence»** منفصل تمامًا عن **محرّك التجارة (Commerce Engine)**. محرّك التجارة مسؤول عن التجارة فقط؛ محرّك النمو معزول تمامًا. **لا اعتماد دائري**؛ يعتمد النمو على التجارة (عبر الأحداث/العقود) ولا تعتمد التجارة على النمو أبدًا.
- **التكامل عبر الأحداث (Event-Driven — المبدأ 14 / ADR-018):** الوحدات القائمة تُصدِر **أحداث دومين مستقرّة** (أسماء وحمولات ثابتة) تشترك فيها وحدات النمو مستقبلًا **دون تعديل أي خدمة قائمة**. الكتالوج المُلزِم للأسماء في [`EVENTS.md`](EVENTS.md). الأحداث تُطلَق `afterCommit`؛ المستمعون الثقال async عبر الطوابير؛ حدث بلا مستمع = نقطة امتداد مشروعة (لا كلفة).
- **جاهزية العميل (Customer):** الحقول التسويقية المستقبلية (تاريخ الميلاد/المناسبة، الجنس، اللغة/الفرع المفضّل، تفضيلات التسويق/التواصل، كود/مصدر الإحالة، شريحة/نقاط الولاء، Customer Score، CLV، متوسط قيمة الطلب، أول/آخر شراء، آخر زيارة، مصدر الاكتساب) تُضاف مستقبلًا **بهجرات إضافية فقط** (جدول امتداد `customer_profiles`/`customer_marketing` أو أعمدة nullable) — **لا تعديل لمخطط 2.10 الآن**. حقول `credit_limit`/`loyalty_points` الموجودة تبقى مواضع جاهزة (ADR-030).
- **جاهزية السلة الذكية (Smart Cart):** نقاط امتداد مستقبلية (Frequently Bought Together، منتجات ذات صلة، توصيات AI، Cross/Up-sell، حزم، عروض ديناميكية، عتبة شحن مجاني ورسائل «أنفق X أكثر»، إضافات مقترحة، حوافز كمية، عروض محدودة الوقت) تُستهلك عبر **أحداث السلة** (`CartCreated/CartItemAdded/…`) دون تعديل `CartService`. لا محرّك توصيات الآن.
- **جاهزية العروض (Promotion):** عقود مستقبلية (حملات، قواعد/شروط/مكافآت العروض، استراتيجيات الكوبونات، مكافآت الإحالة/الولاء، حملات ميلاد/مناسبة/موسمية، Flash Sales) تُطبَّق كطبقة تكامل (عقود + Drivers، المبدأ 13) تستهلك أحداث الطلب/السلة/الدفع. لا تنفيذ.
- **البوابة الوحيدة للتواصل (المبدأ 13):** كل مراسلات النمو المستقبلية (WhatsApp/Email/SMS/Push) **حصريًا عبر طبقة المراسلة القائمة** (`MessagingProviderInterface`/`MessagingManager` — ADR-030). يُمنع أي اتصال مباشر بمزوّد.
- **جاهزية التحليلات:** نقاط امتداد مستقبلية (AOV، CLV، معدّل تكرار الشراء، معدّل التحويل، هجر السلة، أداء التوصيات، ROI الحملات، أفضل الحزم، أداء Cross/Up-sell، شرائح العملاء) تُبنى كمستهلكين للأحداث/مشاريع قراءة (read models) في سياق النمو. لا تقارير الآن.
- **جاهزية إتمام الشراء (Checkout — يطبَّق تصميمًا في 3.2):** يحافظ Checkout والمراحل اللاحقة على نقاط امتداد لـ (طلبات الهدايا ورسائلها، Save For Later، Buy Again، Express/One-Click، استرداد المكافآت/الولاء، سياسات تراكم الكوبونات، التحقّق من العروض، خصومات الميلاد، تسعير AI مستقبلي) **دون تنفيذها** — عبر أحداث Checkout المستقرّة وخُطّافات معطّلة موثّقة.
- **قواعد ملزِمة:** منطق الأعمال في الخدمات؛ المتحكمات رفيعة؛ كل تكامل عبر واجهات؛ الكل provider-independent؛ عزل تام لسياق النمو؛ لا اعتماد دائري.
- **الحالة:** توجيه معماري ووثائق فقط. **صفر كود ميزات نمو.** التنفيذ الفعلي لأي وحدة نمو يستلزم ADR خاصًا في مرحلته.

## ADR-031 — سلة المتجر (Storefront Cart) [مُعتمد في Phase 3.1]
- **السياق:** Phase 3 (المتجر والطلبات) تجمع الوحدات القائمة في مسار شراء العميل (سلة → إتمام → طلب → دفع). لا مخطط جداول مجمّد للسلة؛ تُبنى بنفس المعمارية. تُقسَّم Phase 3 إلى دفعات: **3.1 السلة**، 3.2 إتمام الشراء (تحويل السلة إلى طلب عبر `OrderService`)، 3.3 واجهة المتجر العامة.
- **الكيانات:** `carts` (uuid، soft-delete؛ `user_id`/`customer_id`/`session_token` — سلة نشطة واحدة لكل مستخدم؛ status active/converted/abandoned) + `cart_items` (uuid لا؛ unique(cart, variant)؛ `unit_price` **لقطة سعر الكتالوج** وقت الإضافة).
- **كل المنطق في `CartService`:** `forUser` (سلة نشطة تُنشأ عند الحاجة)، add/set/remove/clear، تسعير من الكتالوج `promo_price ?? retail_price` (لا محرّك تسعير — مؤجّل)، وفحص التوافر `Σ(on_hand − reserved)` عبر المستودعات، ومنع المنتج غير المعروض/غير الفعّال.
- **لا حجز مخزون في السلة (ADR-009):** الحجز يقع عند تأكيد الطلب (3.2/2.6)، لا في السلة؛ السلة تفحص التوافر فقط.
- **العزل والوصول:** السلة **ذاتية النطاق** بالمستخدم المُصادَق (لا تُدار سلات الآخرين)؛ لا صلاحية خاصة (ملكية ذاتية).
- **API:** `/api/v1/store/cart` (عرض/إضافة/تعديل/حذف بند/تفريغ). واجهة المتجر (Blade) تُبنى في دفعة لاحقة (API-First).
- **مؤجّل:** إتمام الشراء (3.2)، واجهة المتجر العامة (3.3)، سلات الضيوف بالجلسة، محرّك التسعير حسب التصنيف.

## ADR-030 — مخطط CRM/العملاء (Customers/CRM Schema) [مُعتمد في Phase 2.10]
- **السياق:** لا مخطط جداول مجمّد للعملاء؛ المجمّد: `BR-CUST-01…14` (إنشاء يدوي/ذاتي، كشف تكرار بالهاتف، تعدد الهواتف/العناوين، وسوم/تصنيفات، عالي الخطورة، حظر، حذف ناعم، دمج) و`orders.customer_id` المؤجّل منذ 2.6. اعتمد المالك معمارية صريحة. لا إعادة تصميم.
- **الكيانات:** `customers` (uuid، soft-delete، auditable؛ `user_id` اختياري — BR-CUST-02؛ حقول `credit_limit`/`loyalty_points` **جاهزة للربط المستقبلي دون إعادة تصميم**؛ `is_high_risk`/`is_blocked`/عدّادات الإلغاء/المرتجعات؛ `merged_into_id`)، و**جداول تابعة**: `customer_phones` (تعدد + أساسي — BR-CUST-05)، `customer_addresses` (تعدد + افتراضي، يشير للجغرافيا — BR-CUST-06)، `customer_contacts`، `customer_notes` (سجلّ زمني append-only).
- **كل المنطق في `CustomerService`:** إنشاء/تعديل مع مزامنة الأبناء (أساسي/افتراضي واحد)، تطبيع الهاتف (أرقام فقط)، كشف التكرار عبر كل الأرقام (BR-CUST-03/05)، ملاحظات، حظر/رفع (BR-CUST-12)، **دمج** (BR-CUST-14: نقل الأبناء والطلبات، تعليم وحذف ناعم للمُدمَج).
- **الربط بالطلبات + لقطة ثابتة:** `orders.customer_id` يُملأ اختياريًا عند إنشاء الطلب (بلا FK صارم — اتساقًا مع 2.6 وسلامة اللقطة)؛ **لقطة العميل على الطلب (الاسم/الهاتف) تبقى ثابتة تاريخيًا** ولا تتأثّر بتعديل العميل لاحقًا. عميل محظور لا يُنشئ طلبات (BR-CUST-12).
- **جاهزية التكامل (المتطلّب):** طبقة مراسلة provider-agnostic — عقد `MessagingProviderInterface` + `MessagingManager` + Null Driver + `config/messaging.php` (قنوات whatsapp/email/sms/marketing) — جاهزة لربط مزوّدين لاحقًا دون لمس منطق CRM. حقول العميل تسمح بالربط المستقبلي بنقاط الولاء/الائتمان/الفواتير/الطلبات/الشحن/المحاسبة دون تغيير المخطط.
- **الصلاحيات:** `crm.customers.{view,create,update,delete,block,merge}` (ADR-021)؛ للمدير كامل، المبيعات إنشاء/تعديل، المسوّق/المحاسب قراءة.
- **مؤجّل بخُطّافات:** مزوّدو المراسلة الفعليون، محرّك التسعير حسب التصنيف (BR-PRICE)، احتساب "عالي الخطورة" التلقائي، حساب دخول العميل (`user_id`).

## ADR-029 — محرّك المحاسبة بالقيد المزدوج (Double-Entry Accounting Engine) [مُعتمد في Phase 2.9]
- **السياق:** ADR-016 يفرض قيدًا مزدوجًا وعكسًا لا حذفًا و`journal_lines` بلا soft-delete، و BR-ACC-01…11 تحدّد الأحداث المولّدة للقيود والتوازن والعزل عبر الأحداث. لا مخطط جداول مجمّد؛ اعتمد المالك معمارية صريحة. لا إعادة تصميم.
- **الكيانات:** `accounts` (دليل حسابات شجري، أنواع asset/liability/equity/revenue/expense، أوراق قابلة للترحيل)، `fiscal_years` + `accounting_periods` (تعدد السنوات — المتطلّب 7)، `journal_entries` (uuid، `JE-{YYYY}-{seq}`، draft→posted)، `journal_lines` (append-only بلا updated_at/soft-delete — مصدر الحقيقة).
- **القيد المزدوج (المتطلّب 1/3، BR-ACC-10):** كل قيد سطراه ≥2، كل سطر مدين XOR دائن، ومجموع المدين = مجموع الدائن (يُرفض غير المتوازن). الترحيل داخل معاملة.
- **عدم القابلية للتعديل (المتطلّب 2/8، BR-ACC-09):** القيد المُرحّل و`journal_lines` غير قابلة للتعديل/الحذف (حرّاس على مستوى النموذج). التصحيح **بقيد عاكس فقط** يقلب المدين/الدائن ويشير للأصل عبر `reverses_entry_id`؛ حالة "معكوس" تُشتقّ (لا نعدّل الأصل).
- **الأرصدة مشتقّة (المتطلّب 4):** رصيد أي حساب = Σ(مدين)−Σ(دائن) للسطور المُرحّلة (بطبيعته)، وميزان المراجعة يُبنى من الدفتر. **لا رصيد مخزَّن.**
- **العزل عبر الأحداث (المتطلّب 6، BR-ACC-11):** `AccountingService` يحوي كل المنطق؛ حدث `FinancialEventOccurred` تُطلقه الوحدات، ومستمع `PostFinancialEventToLedger` (متزامن) يولّد القيد عبر `AccountingService::recordEvent` بخريطة حسابات من `config/accounting.php`. المحاسبة لا تعرف الوحدات؛ التكامل مع المبيعات/المشتريات/المخزون/المدفوعات/الاسترداد/الضرائب/الشحن **مستقبلي** بإضافة خرائط أحداث دون تعديل الكود (المتطلّب 5/7).
- **الصلاحيات:** `accounting.accounts.{view,manage}`، `accounting.journal.{view,create,post,reverse}`، `accounting.reports.view` (ADR-021)؛ للمدير والمحاسب.
- **مؤجّل بخُطّافات:** الخزائن/البنوك التفصيلية، الضريبة الفعلية، القوائم المالية الكاملة، تعدد العملات التشغيلي، وربط أحداث الوحدات فعليًا — كلٌّ في مرحلته دون إعادة تصميم.

## ADR-028 — مخطط المدفوعات وطبقة تكامل المزوّدين (Payments Schema & Provider Integration) [مُعتمد في Phase 2.8]
- **السياق:** لا مخطط جداول مجمّد للمدفوعات؛ المجمّد: مفردات `payment_statuses` (unpaid/partially_paid/paid/refunded)، ADR-016 (خطّافات محاسبية مؤجّلة)، ADR-018 (أحداث)، Idempotency-Key. اعتمد المالك معمارية Provider/Integration صريحة. لا إعادة تصميم لنموذج الأعمال.
- **طبقة التكامل (المبدأ 13/ADR-019):** عقد موحّد `PaymentProviderInterface` (charge/capture/verify/refund/name)؛ كل المزوّدين خلفه + Driver. `PaymentProviderManager` هو النقطة الوحيدة لإنشاء مزوّد (يربط `payment_methods.driver` بصنف من `config/payments.php`). **المزوّدون يُوصَلون حصريًا عبر هذه الطبقة — لا استدعاء مباشر من متحكم/خدمة (المتطلّب 6).**
- **إضافة مزوّد دون لمس منطق الطلب/الدفع (المتطلّب 3):** صفّ في `payment_methods` يشير إلى Driver مُسجَّل. Drivers الحالية: `offline` (COD/تحويل بنكي — تحصيل يدوي، فعّال) و`null` (بوابات أونلاين غير مُهيّأة — placeholder آمن). مُهيّأة كـ placeholders معطّلة: HyperPay/MyFatoorah/Stripe/PayPal/Moyasar.
- **الكيانات:** `payment_methods` (سجلّ)، `payments` (uuid/soft-delete/auditable، ترقيم `PAY-{YYYY}-{seq}`)، `payment_transactions` (append-only — بنية عامة لمراجع/حالات/callbacks/بيانات أي مزوّد، المتطلّب 5).
- **حالة سجلّ الدفع:** pending → processing → paid | failed | cancelled | (paid →) partially_refunded/refunded (حالة تقنية داخلية).
- **حالة دفع الطلب (مشتقّة):** أُضيف `orders.payment_status` (مفردات payment_statuses) و`amount_paid` — تُعاد اشتقاقها من المدفوعات المقبوضة ناقص المُسترَد؛ تدعم الدفع الجزئي والتراكمي والاسترداد.
- **الصلاحيات:** `payments.{view,create,capture,refund}` + `payments.methods.manage` (ADR-021)؛ المحاسب كامل عمليًا، المبيعات view/create، المستودع view/capture (تحصيل COD عند التسليم).
- **مؤجّل بخُطّافات:** أي تكامل بوابة محدّدة، الأثر المحاسبي/الخزائن (2.9)، Idempotency-Key (عابر للنظام)، تسويات/إشعارات دائنة.

## ADR-027 — مخطط الشحن وطبقة تكامل التوصيل (Shipping Schema & Delivery Integration) [مُعتمد في Phase 2.7]
- **السياق:** لا مخطط جداول مجمّد للشحنات (مؤشّرة "Phase 3" في `API_CONTRACT §378`)؛ الجغرافيا مجمّدة في `PHASE_2_DESIGN §3–6` لكنها لم تُبنَ؛ تسعير الشحن مؤجّل صراحةً (§149/§187). يُنزِل هذا القرار قواعد ADR-014/010/BR-ORD-10 إلى مخطط تنفيذي (وثيقة `PHASE_2_7_SHIPPING_DESIGN.md`) — لا إعادة تصميم لنموذج الأعمال.
- **الجغرافيا:** تُبنى `governorates`/`cities`/`areas`/`shipping_zones` (+ جدولا ربط) **بحذافير §3–6 بلا أعمدة إضافية**. المحلي مرجع النظام.
- **التكامل (تعيين متعدد المزوّدين):** سجلّ `delivery_providers` + جدول تعيين polymorphic `geo_provider_mappings` (`delivery_provider_id`, `external_id`, `external_code`, `provider_metadata`, `last_synced_at`, `sync_status`, `is_active`) — تعيين السجلّ المحلي الواحد لعدّة مزوّدين في آنٍ؛ تعطيل/استبدال مزوّد دون فقد بيانات محلية.
- **الشحنات:** `shipments` (uuid/soft-delete/auditable، ترقيم `SHP-{YYYY}-{seq}`) + `shipment_events` (append-only). لقطة عنوان + معرّفات مُعيَّنة (`area_id`/`city_id` لا اسم — يمنع الحساب من الاسم)؛ لقطة تكلفة ثابتة؛ `delivery_provider_id` لمزوّد واحد.
- **آلة الحالات:** `not_shipped → in_transit → out_for_delivery → delivered` (+`failed`، وحالات تشغيلية `delayed`/`customer_unavailable`) — تُكمل جزء التوصيل من ADR-010/BR-ORD-10 الذي أجّلته 2.6، وتُزامن حالة الطلب. لا تكرّر خصم المخزون (يبقى في `OrderService::ship` — 2.6).
- **طبقة التكامل (المبدأ 13/ADR-019):** عقود `DeliveryProviderInterface`/`GeographySyncProviderInterface`/`ShippingQuoteProviderInterface` + **Null Drivers**، تُربط عبر `config/shipping.php`. الوصول للمزوّد حصريًا عبر هذه العقود المحقونة — لا استدعاء مباشر من متحكم/نموذج.
- **مُحلّل التكلفة (أولوية/احتياط):** عرض حيّ → أحدث مُزامَن → سعر منطقة → تجاوز يدوي (بصلاحية `shipping.override_cost`) → مراجعة يدوية. **الفعّال في 2.7:** الحيّ (Null ⇒ غير متوفّر) واليدوي/المراجعة؛ المستويان المُزامَن/المنطقة مُعرّفان ومؤجّلان. النتيجة **لقطة** على الشحنة والطلب.
- **الصلاحيات:** `shipping.shipments.{view,create,update,dispatch,deliver,fail}` + `shipping.override_cost` + `settings.geography.{view,manage}` (ADR-021).
- **مؤجّل بخُطّافات:** محرّك تسعير الشحن الفعلي، أي مزوّد محدّد، المزامنة الحيّة، المدفوعات/COD، الاعتراف المحاسبي، كيان العملاء/العناوين — كلٌّ لمرحلته.

## ADR-026 — مخطط طلبات البيع (Sales Orders Schema) [مُعتمد في Phase 2.6]
- **السياق:** وثائق التصميم المجمّدة (`PHASE_2_DESIGN`, `DATA_DICTIONARY`, `DESIGN_REVIEW §9`) تحصر Phase 2 في 6 دفعات تنتهي عند المخزون وتؤجّل الطلبات إلى "Phase 3" دون مخطط جداول؛ **قواعد الطلب مجمّدة** (ADR-009/010/010a، BR-ORD-01…18، مفردات الحالات). يُنزِل هذا القرار تلك القواعد إلى مخطط تنفيذي (وثيقة `PHASE_2_6_SALES_ORDERS_DESIGN.md`) — لا إعادة تصميم.
- **الكيانات:** `orders` (+`order_items`) + `order_status_history` (append-only). الرأس: uuid + soft-delete + Auditable؛ البنود بلا uuid/soft-delete؛ السجلّ بلا updated_at/soft-delete.
- **الترقيم (ADR-002):** `SO-{YYYY}-{seq}`.
- **العميل:** **لقطة مضمّنة** (`customer_name/phone/email/shipping_address`) + عمود `customer_id` **مؤجّل بلا FK** (يُربط بكيان CRM في 2.10) — تفاديًا لبناء CRM قبل أوانه.
- **آلة الحالات:** تقرأ مفاتيح الحالات من `order_statuses` القابل للإدارة (ADR-017)؛ المنفَّذ: `draft → confirmed → stock_reserved → preparing → ready_to_ship → shipped → delivered` + `cancelled`. الحالات التشغيلية/المرتجعات (`out_for_delivery`/`delayed`/`returned`…) **مُعرّفة في القاموس وممنوعة تنفيذيًا** حتى مراحلها (الشحن/المرتجعات).
- **توقيت المخزون (ADR-009، إلزامي عبر خدمات المخزون فقط):** حجز عند `stock_reserved` (`reserve`)؛ استهلاك + خصم نهائي بـ WAC عند `shipped` (`consume` + `sale_out`/COGS)؛ تحرير عند الإلغاء قبل الشحن (`release`). لا مسّ مباشر لجداول المخزون.
- **إضافة `ReservationService::consume`:** تنفيذٌ لمفردة الحجز المجمّدة `active → consumed` ("عند الشحن") — لا ميزة جديدة.
- **تجميد سعر البند (BR-ORD-18):** `order_items.unit_price` لقطة وقت الإنشاء (لا محرّك تسعير بعد — مُدخل يدويًا).
- **تسجيل الانتقالات (BR-ORD-09):** كل انتقال يكتب صفًّا في `order_status_history` (from/to/by/note) داخل معاملة.
- **مؤجّل بخُطّافات:** التسعير/الضريبة/الشحن (2.7)/المدفوعات (2.8)/الاعتراف بالإيراد وCOGS محاسبيًا (2.9)/العمولة/المرتجعات/CRM (2.10)/قنوات web/POS. الأعمدة والمعالم الزمنية جاهزة للربط دون إعادة تصميم؛ **إطلاق أحداث الدومين مؤجّل** إلى مراحلها (تفاديًا لمستمعين فارغين).

## ADR-024 — المتغيّرات كأساس للمخزون (Variants as Inventory Substrate) [مُعتمد في Phase 2.4]
- **السياق:** يُمسك المخزون في التصميم لكل **(متغيّر × مستودع)** (§22)، وكل كيانات المخزون تشير إلى `variant_id`→`product_variants` (§17). لكن `product_variants` لم يُبنَ في 2.2/2.3، والمخزون (2.4) يحتاجه. الربط على `product_id` بدلًا منه = **إعادة تصميم** (مرفوض).
- **القرار:** إنشاء `product_variants` (§17) كأساس أدنى للمخزون:
  - **متغيّر افتراضي واحد** يُنشأ تلقائيًا لكل منتج عبر `ProductService` (`is_default=true`، يعكس sku المنتج)؛ المنتج البسيط = وحدة تخزين واحدة.
  - المخزون وكل عملياته تُمسك على مستوى المتغيّر (وفاءً كاملًا للتصميم).
  - **إدارة المتغيّرات الكاملة** (تعدد المتغيّرات، تركيبات السمات، واجهة المتغيّرات) **مؤجّلة**؛ 2.4 يحتاج **سجلّات** متغيّرات فقط لحمل المخزون.
- **الترقية:** backfill للمنتجات القائمة بلا متغيّر افتراضي (idempotent).
- **الأثر:** لا إعادة تصميم؛ إضافة substrate يتبع الأعراف (uuid، soft-delete، auditable).

## ADR-022 — الجداول الداعمة والكيانات المؤجلة [مُعتمد في مراجعة التصميم]
- **الجداول الداعمة (Pivots/Children)** خارج الـ27 لكنها جزء طبيعي من Phase 2: `shipping_zone_city`, `shipping_zone_area`, `variant_attribute_value`, `product_tag_links`, `stock_adjustment_items`, `warehouse_transfer_items`. مقبولة ولا تُعدّ توسّعًا للنطاق.
- **كيان `approval_requests`** (طلبات الاعتماد العامة) و**مفاتيح إعدادات مقترحة** (`pricing.discount_approval_threshold`, `purchasing.po_approval_threshold`, `inventory.adjustment_value_threshold`, `affiliate.min_payout`, `notifications.quiet_hours`): **مقبولة كتصميم**، تُنشأ في مرحلتها المناسبة (الاعتمادات في Phase 3+، لا في Phase 2). لا حاجة لتعديل نطاق Phase 2.

| 9 | `reports.view_financial` مقابل `pricing.view_cost` | **صلاحيتان منفصلتان** (رؤية التكلفة ≠ التقارير المالية) | ADR-013/021 |
